## A Quick Clarification: 401 vs. 400
- Picking up from the previous session's Basic Authentication discussion, a precise distinction is made directly: *"the user gave the correct username and password wrong. Ok, the user gave the wrong username and password right. Then also 401 will be unauthorized. The user didn't send the username and password at all. 400 is a bad request... because the required field should be compulsory. It is not sending."*
- **The practical value of knowing this distinction, stated directly**: *"by knowing this, we can guess that we have made a mistake. By guessing, we can check where to check properly."* A **400** on an auth-protected endpoint suggests a missing required field (e.g. the Authorization header itself); a **401** suggests the field was present but the credentials inside it were wrong.

## Rate Limiting Policy — Fixed Window Algorithm
- **The core mechanism, defined directly with a concrete numeric example**: an API expects roughly 100 requests per minute of real capacity; a Rate Limiting policy is set to **95 per minute** as a safety margin. *"What if the 96th request comes in 1 minute? What will it do? It will reject the last 96th request. 96, 97, 98 will be rejected."*
- **Why this matters at all, motivated by a real-world crash scenario**: *"there are situations like WhatsApp has crashed, Facebook has crashed, etc. One of the reasons is that there is too much traffic than expected traffic, which the servers cannot handle."* Rate Limiting exists to reject excess traffic outright before it can overwhelm the server, rather than trying to process everything and crashing.
- **What Rate Limiting does NOT do, clarified directly**: it doesn't queue excess requests — *"what will it do if more requests come? It will put it in the poll [pool/queue]. No, it will reject it. Directly reject it."* (Queuing is explicitly reserved for the separate Spike Control policy, covered later in the same session.)
- **The fixed window algorithm, worked through carefully with a live example**: if the window is 1 minute and the first request arrives at 10:01, the quota window runs 10:01–10:02, then resets 10:02–10:03, and so on. **A live worked example of what happens across two windows**: 95 requests arrive in the first 30 seconds of a window; a further 95-or-100 requests arrive in the remaining 30 seconds of that *same* window — the second batch, since it falls within the already-consumed quota, gets rejected once the 95 limit for that window is hit, regardless of which half of the window it fell in.
- **The exact rejection response, given directly**: **HTTP 429 — "Too Many Requests"**. **Why a 400-series code specifically, explained directly**: *"we have already informed them not to send more than this. That's it. Rate Limiting is a policy, it is a contract between the consumers and us. We will not be able to process more than this. That's why 400 series."*
- **When the window "clock" actually starts, clarified with a direct, deliberately-repeated example**: the window begins from the moment of the **first request the application receives after (re)deployment or restart** — *"if we redeployed the application in the middle... after redeploying, the application was redeployed at 10.05. But the first request came at 10.06. Then, the first time the rate limiting number will be taken, the time will be 10.06."* The instructor explicitly flags this as a point *"99.99% for people"* — i.e., almost everyone gets confused about it initially, and it's worth repeating and confirming understanding of directly.
- **Scope is per-application, not per-consumer, clarified directly**: with 3 consumers sending requests to the same rate-limited API, the 95-per-minute quota is shared across **all** consumers combined, not given separately to each one — *"is it 95 for each of them or 95 for all? ... because we are handling our application in the application, so only 95 will handle our application. That is why it is 95 for all of them."*
- **A direct, honest note on how often this is actually used in practice**: *"this policy is applied more in real time. It is less [used]... when we do it in cloud hub, it will handle more number of requests as well and such situations will have less implementation."* **The realistic scenario where it does matter, given directly**: protecting your own API's actual measured capacity (established via load/performance testing — e.g. tested up to 2000 requests/hour successfully, but crashing around 3000 with the current worker count) or respecting a **third-party API's own published rate limit** (e.g. a vendor capping you at 10,000 requests per hour) that your own design must not exceed.
- **A direct, explicit interview-relevance callout**: *"if I say that only basic authentication worked, we can say that I got 3-5 years of mule software experience... it won't be good. Even if you get the opportunity in real time or not, at least you should present yourself that you have experience on these policies."*

## Rate Limiting SLA — Tiered Limits Per Consumer
- **The scenario motivating this separate policy, given directly**: a commercialized API with **silver, gold, and diamond membership tiers**, each entitled to a different request-rate allowance — something plain Rate Limiting cannot express, because it applies one shared limit across everyone: *"now I have a silver member, a gold member and a diamond member for my API... can I implement it in rate limiting policy? I can't. Everything is common there."*
- **Real-world monetization framing, given directly**: *"do you always give your APIs for free? Yes, we do. Sometimes we expose our API to outside parties. We charge those outside parties. Because we provide API services."*
- **Illustrative (deliberately simplified) numbers given directly**: silver = 1 request/minute, gold = 2 requests/minute, diamond = 5 requests/minute — explicitly caveated as arbitrary placeholder numbers for teaching purposes, not realistic production values.
- **The mechanism, tied directly back to Client ID Enforcement**: *"if you observe, when we do client ID enforcement, do we generate client ID client secret to each client? That's it."* — Rate Limiting SLA works by creating **SLA tiers**, then referencing/tagging a specific consumer's Client ID to a specific tier, so the enforced limit is genuinely per-consumer rather than shared.
- **The precise difference from plain Rate Limiting, stated directly**: *"Rate Limiting policy is for the entire API and... it will calculate the total number of requests received from the total consumers in that particular time frame and it will reject irrespective of the consumer... here the limit is specific to each consumer or each client... if the consumer exceeds the limit then only the request will be rejected with 429."*
- **A direct, honest personal admission about real-world usage**: *"if you ask me, I have never implemented rate limiting SLA in my total experience. But if you go for an interview, you will get all these questions."*

## Real-World Correlations: Netflix, Prime Video, Antivirus Software
- **A direct real-world analogy drawn to make the tiered concept concrete**: *"Prime video, Netflix, Aaha video, etc... if you have a free account, you can access many things. If you have a premium account, you can access many things... there are two levels for premium users... level 1 has 5 devices. If you use more than 5 devices, will there be an error? Yes... level 2 has unlimited devices."*
- **Antivirus software given as a second directly-cited example of the same underlying pattern**, licensed per number of devices.
- **The pedagogical point made explicitly**: *"we might be applying somewhere [these concepts already, in everyday consumer products]. But finally, we don't know that terminology... here, it is called rate limiting policy."* — recognizing that the concept of tiered, per-consumer limits is already familiar from everyday products; the point is connecting that intuition to the correct MuleSoft policy name and mechanism.
- **A direct clarification that rate limiting is a universal API concept, not MuleSoft-specific**: *"is this rate limiting policy common only to MuleSoft? No... it's a common terminology applicable for almost like all API levels... these are the policies. Rate Limiting is a common policy. But we are looking at how to implement that policy in MuleSoft."*

## Spike Control — Queuing Instead of Rejecting
- **The core distinguishing behavior vs. Rate Limiting, stated directly**: *"there is a rate limit... but if it doesn't happen [get accepted immediately], this spike control policy shouldn't reject us. After the window is finished, if the window is exceeded, that request will be placed in the queue... after the window is opened, it will try to process the message from the queue."*
- **Also known as throttling, clarified directly**: *"some people call it throttling. Actually, throttling is a generic name... but in MuleSoft, it is called Spike Control Policy."*
- **A crucial trade-off surfaced through direct back-and-forth questioning**: since the request is queued rather than immediately rejected, the caller must wait longer for a response — *"if I save it in the queue, will I still be able to give a response to them? They will get a delayed response."* This is explicitly examined against the **request-reply pattern**'s expectation of a timely response: *"the user experience should not go that far in the request-reply pattern... that's why it keeps a short time frame."* A deliberately extreme counter-example (keeping requests queued for a full 30 minutes) is directly rejected as bad design: *"is this policy right or wrong? It is wrong."*
- **The sliding window algorithm, explained directly in contrast to the fixed window used by Rate Limiting**: rather than resetting cleanly at fixed clock boundaries (10:01→10:02→10:03), a sliding window continuously "looks back" a fixed duration from the *current* moment — *"what that window does is, suppose we say 5 seconds now... it will take 5 seconds from the fifth request to the back... the window will be sliding."* **The stated advantage of this approach**: *"the advantage of this sliding window is that we have a scope to handle more requests in less time"* — because capacity can free up continuously as older requests age out of the trailing window, rather than only at fixed reset boundaries.
- **A detailed worked numeric example given live**: a window of 5 requests per 30 seconds; if 5 requests land within the first 25 seconds and only 1 of them falls within the most recent 5-30-second lookback at the moment a 6th request arrives at second 25, the sliding window recalculates from that exact moment backward and may find capacity available even though the *fixed*-window equivalent would have already been exhausted.
- **Why short time frames specifically make sense for Spike Control, tied directly back to the request-reply constraint**: *"since we should not do it for a long time, we would have planned to respond within 5-10 seconds. Overall. If it takes more time than that, obviously the timeout is over and we reject it."*

## HTTP Caching Policy — When Frequently-Requested Data Doesn't Change Often
- **The motivating third-party-cost example, given directly and concretely**: a **PAN verification API** (India-specific; PAN numbers issued by the NSDL organization) charged **10 rupees per call** — used for a loan applicant's PAN, verified **three times in the same day** (e.g., for a two-wheeler loan, a home loan, and a third check) costing **30 rupees total** for data that hadn't actually changed. **The fix, described directly**: *"he applied a policy called caching here. Within a day, how many times does a pan number come? I will charge it once... first request came... collected all the details. Saved in cache... second request came... it is there. Cache."*
- **A second, internally-focused example given directly**: an HR database's list of employees who resigned in a given month (e.g., 25 in November, 50 in October) — data that changes slowly enough that repeated identical requests from different HR consumers within a short window can safely be served from cache rather than re-querying the database each time.
- **A direct discussion of choosing an appropriate cache duration**: *"how many days do we have to save?... let's say we give 15 days. In these 15 days, thousands and thousands of requests will come... if we save all those responses in the cache, will the cache memory also get disturbed? That's why we keep it like that for 1-2 days."* The caching window has to balance genuine reuse value against cache memory pressure.
- **The general rule for when HTTP Caching applies, stated directly**: *"whenever there is a possibility of retrieving frequently non-changing data, in such a situation, can I use this HTTP caching?"* — Yes, precisely for that shape of data (frequently requested, infrequently changed).
- **A direct interview-seniority note**: *"this HTTP Caching Policy... I will ask based on my seniority. I will ask for 5 to 8 years. Below 5 years, I will ask about rate limiting, spike control, OAuth, basic auth, client ID."*

## JSON Threat Protection Policy — Gateway-Level Payload Restrictions
- **The core motivating scenario, given directly**: an API Kit Router passes a request into the application, but the payload itself might be enormous or maliciously oversized — *"the request that the router passes to the API and the API is unable to handle the memory. Because the message they send is huge... how to restrict it? This is Jason Threat Production Policy."*
- **The specific restrictions this policy can enforce, listed directly**: minimum/maximum string length, maximum number of properties on an object (illustrated with a scenario of a request maliciously sending "one lakh" — 100,000 — properties instead of 5), and maximum **nesting/container depth**.
- **The critical distinguishing point vs. defining the same constraints in RAML, made directly and precisely**: RAML-level (or API Kit Router-level) validation still happens **after** the request has already entered the application and memory has already been allocated for attributes/body — *"the listener will come inside and get validation from API Kit Rotor. That's it? Yes. So, did it enter into the API or not? It entered. But what if it does here? Before the API enters. So, it should enter in the gateway itself... this is more secure."* JSON Threat Protection, applied at the **gateway** level, rejects an oversized/malformed payload **before** it ever reaches the listener or consumes application memory at all — a meaningfully stronger defense against resource-exhaustion attacks.
- **`additionalProperties`, connected back to earlier RAML concepts**: the default RAML behavior of allowing extra, undefined properties (`additionalProperties: true` by default) is directly named as one concrete way an attacker or careless client could send far more data than expected — reinforcing why a gateway-level hard cap on property count is valuable independent of RAML's own schema rules.

## IP Allow List and Block List — Briefly Introduced
- **The mechanism, defined simply and directly**: *"I will process the request from these IPs only [Allow List]... otherwise, now my request is [some other IP]. Will the API accept it or not? It won't."* The Block List works as the direct inverse: specific IPs are explicitly rejected while everything else is allowed.

## Quick Recap
- **401 means bad credentials were sent; 400 means required credentials/fields were missing entirely** — a useful diagnostic distinction.
- **Rate Limiting uses a fixed window algorithm**, is scoped to the **entire application, not per-consumer**, rejects excess requests outright with **429 Too Many Requests**, and its window clock starts from the first request after deployment/restart — a subtlety almost everyone misunderstands initially.
- **Rate Limiting SLA** enables genuinely per-consumer tiered limits (silver/gold/diamond-style) by combining SLA tiers with Client ID Enforcement's per-client identity — something plain Rate Limiting structurally cannot do.
- **Rate limiting concepts map directly onto everyday consumer products** (Netflix/Prime device limits, antivirus device licensing) — the underlying idea is familiar even when the MuleSoft terminology isn't.
- **Spike Control queues excess requests instead of rejecting them outright**, using a **sliding window algorithm** (continuously re-evaluated from the current moment, unlike Rate Limiting's fixed clock boundaries) — but its request-reply-pattern constraints mean it must use short time frames and few retry attempts, or user experience degrades badly.
- **HTTP Caching Policy** is for frequently-requested, infrequently-changing data (illustrated with a PAN-verification cost example and an HR resignation-list example) — with cache duration chosen to balance reuse value against cache memory pressure.
- **JSON Threat Protection Policy**, applied at the **gateway level**, restricts string length, property count, and nesting depth **before** a request ever enters the application — genuinely more secure than equivalent RAML-level validation, which only runs after memory has already been allocated for the request.
- **IP Allow List / Block List** restrict access by source IP, in either an inclusive or exclusive direction.
- **The genuinely most-used policies in real practice**: Basic Auth, Client ID Enforcement, Rate Limiting, Spike Control, and OAuth — with OAuth dominant at the Experience layer and Client ID Enforcement dominant for internal Process/System communication.
