# Day 26 — Publishing to Exchange and Importing a Published API Into Studio

## Session Agenda

## Why Publish to Exchange — the Direct Justification
- The session opens with a pointed rhetorical question: after building the full API specification (base + imported fragment), you *can* technically keep working with it unpublished — so why publish at all? **The direct, standard-industry answer given**: *"as soon as our API specification is ready, we will immediately publish it to Exchange."* Two concrete reasons follow:
  1. **To import it into Anypoint Studio** — Studio's import mechanism pulls from Exchange, not from a local file, in normal practice.
  2. **To apply policies in API Manager** — when you create an asset in API Manager for a given API, that asset is also sourced from Exchange. Both workflows have a hard dependency on the spec already being published there.
- **The broader framing, stated directly**: Exchange is *"a central repository where all MuleSoft assets will be saved and published"* — and it's not developer-only; other Anypoint Platform modules themselves consume the specification from Exchange.

## Exchange's Asset Model
- **"All Assets"** = both MuleSoft-provided assets and the organization's own created assets, combined in one view.
- **"Provided by MuleSoft"** (called out by name in the transcript as "E-PAM," likely a mis-transcription of "provided by MuleSoft"): the organization's own account groups its published API specs and fragments here — *"if we have 100 API specifications, where will they be? They will be classified under [provided by MuleSoft, i.e. under your org account]."*
- **"Shared with Me"**: anything explicitly shared with you by a colleague lands here.
- **"My Applications"**: your own published assets.
- **Public Portal**: the mechanism for sharing an API spec with people *outside* the organization for testing — covered in detail below.
- **Asset types, demonstrated directly by filtering**: when the instructor filters Exchange by type for their own org's assets, only **two types** show up because the org has only published REST APIs and Fragments so far. But Exchange as a whole (via "All Assets") supports far more: **connectors, custom-related assets, DataWeave libraries, examples, policies, Fragments, REST APIs, SOAP APIs, templates**, and more — *"in any point exchange... we can save many types of assets. It's not like we will only save this."*
- **How the type gets set on publish**: publishing directly from **Design Center** or **Exchange** auto-detects the type (API specification or fragment) — *"it already knows it... so that classification is done automatically."* But publishing **from scratch** (e.g. a template project you built yourself) requires you to manually specify the name, asset type (example project? API? SOAP? REST? Async?), and lifecycle status (**Development** vs. **Stable**) yourself.
- **A live example of browsing MuleSoft-provided connectors**: filtering "Provided by MuleSoft" → Connector shows an alphabetically-sorted list — Salesforce Connector, S4 HANA Connector, SIP Connector, Amazon S3 Connector, Trilio, MongoDB, Einstein Analytics, Workday Connector, and many more. **The direct callback to earlier lessons**: this is exactly where Studio's "Add Modules" search pulls a connector from if it isn't already in your project — you connect your Anypoint account and import from here, the same mechanism used earlier for Secure Properties.

## Sharing and Testing Directly From Exchange
- Exchange lets you **test the API directly in the browser** — the same design-center-style request/response UI (e.g. testing the `employees` POST resource) is available from within the Exchange asset page itself, without needing Studio or Postman.
- **Two sharing mechanisms, precisely distinguished**:
  1. **Share → Collaborators (by email)** — invite a specific person in your organization via their email; they land in their own "Shared with Me."
  2. **Public Portal** — toggle a specific version to **Public**, save, and Exchange generates a shareable URL. *"If I share this URL to the person who wanted to test this, anyone can test this... it's a public portal."* Anyone with the link can hit and test the API — demonstrated live, including a deliberately broken request (a removed comma) correctly producing an **"Invalid schema"** error, proving the schema validation is real and live even through the public portal.
- **The default-visibility point, stated directly**: once published normally (not via public portal), *"it will be accessible to all the developers who are part of that organization"* automatically — no additional sharing step needed for internal visibility.

## Creating the Project and Importing the Published API
- **New project creation**: File → New → Mule Project (or right-click in the project explorer). Project named `HR employees` in the demo.
- **Runtime selection and Install Runtimes**: Studio shows available server/runtime versions (3.0 through 8.1 demoed) with an **Install Runtimes** option if the one you need isn't present. The demo proceeds with **4.4.0** without installing.
- **The three import options at project creation, compared directly and precisely**:
  1. **Import a published API** — pulls the specification already published to **Exchange**. **Stated as the one actually used in real-time practice**: *"most of the time, we use import-published API."*
  2. **Import RAML from local file** — imports a downloaded `.zip` of the spec (obtainable via Design Center's own **Download** button, producing a structured zip). **Direct honesty about how rarely this is actually used**: *"in real time, most of the time they don't do that. They publish it and import it here."* Its real use case: **when SSL/connectivity issues** prevent Studio from talking to the Anypoint Platform directly — a fallback, not the norm.
  3. **Download RAML from Design Center** — Studio connects directly to Design Center (rather than Exchange) using your platform credentials. **The precise reason this is generally preferred over relying purely on a static export**: *"whenever we make any changes in the design center... to reflect all this here in the studio, there will be a seamless connection between the exchange and the studio. The latest versions will also be available here."* Design Center itself lacks that same seamless, always-current integration compared to Exchange.
  - **Net conclusion, restated directly**: despite three options existing, **Import Published API (from Exchange)** is what's genuinely used day-to-day.
- **Live import walkthrough**: click **+** next to dependencies → **From Exchange** → log in with Anypoint Platform credentials → **Add Account** → select the correct **organization domain** (here, an example "ICICI-Bank" custom SSO domain — *"either you can get it from your colleagues or... if we don't have the permission, you can ask your colleagues"* for the domain name) → sign in → the published version (`1.0.0`) appears and is selected for import.
- **Scaffold Flows vs. Default Workspace, at the finish step**:
  - **Workspace**: the folder where all Anypoint Studio projects physically live (callback to an earlier-session example folder, `D:\WSAPS`). Demo uses the default.
  - **"Scaffold flows from these API specifications"** — precisely explained: *"there are resources and methods. A flow will be generated for each resource method. And a main flow will be generated."* Concretely: a **listener flow** is generated (all requests land here), plus an **API Kit Router** component that inspects each incoming request against the specification and routes it to the matching resource-method flow (post/patch/get). **This entire generation process is what "scaffolding" means.**
  - **A direct honesty note about scaffolding failure modes**: scaffolding failing due to a broken spec shows up as a **red error symbol** in the project — but a spec that's merely *structurally imperfect* (not fully broken) can still succeed at scaffolding without visibly failing, which is precisely why you must still separately test your flows properly rather than trusting a clean scaffold as proof of correctness.

## The Generated Project Structure and the Golden Rule of Flow Naming
- After scaffolding, the project structure should have `src/main/mule` at the top (a brief hiccup in the demo where the layout looked different was noted but not a real problem).
- **How flow names are generated, and why they matter enormously**: each generated flow is named after its resource-method pair, e.g. `post:\employee` (shown at exaggerated repetition in the transcript, apparently a transcription artifact reflecting the instructor repeating the exact flow name for emphasis).
- **The golden rule, stated directly and unambiguously**: *"post or application should be in the same order as this order... same goes for every resource, every flow. These three flows should also be in the same order... If I change this, the API Kit Router will be confused and it will not understand where to send it."* The API Kit Router matches on this generated name pattern; renaming (or reordering the underlying pattern) a scaffolded resource-method flow's name breaks routing. **Direct guidance on what's actually safe to change**: *"we can change other flow names, no problem. But we should not change these flow names"* — meaning the auto-generated resource-method flow names specifically must stay untouched, even though other custom/private flows you create yourself can be named freely.
- **How the router actually knows where to send requests**: clicking into the API Kit Router component reveals an auto-generated **router configuration** (e.g. `HR-employees-config`), whose **API Definition** field points at the imported API specification (including any imported fragment, e.g. "common headers fragment" visible as already present). *"Does the router have all the information or not?... Post request will check the data type. In the request that has come, will it have all the data type or not? If it has, it will send it to the post. Otherwise, it will reject it."*
- **A live, concrete example of extending an existing production API**: a scenario is framed where 3 resources already exist, live in production, built by another developer, and the task is to **add a 4th resource** — done by returning to Design Center, adding the new resource with its own data types/examples, republishing (bumping the version, e.g. to a new `1.0.x`), and re-pulling it into the existing Studio project. **The same golden rule is reiterated in this context**: *"before we go to production, we will decide on the name of the resource. We should not touch anything for this order or combination."*
- **Main flow anatomy, clarified**: the generated **API Console flow** is also technically a "main flow" structure (source + processing + error handling) but is described as typically **deleted in real-time projects** — it exists mainly for **API Kit Console—based testing** (a lightweight built-in test UI), which is *"not required 90% of the time."* The instructor explicitly deletes it in the demo.
- **Main flow vs. private (sub)flow, precisely distinguished**: *"if there is no source, we call it private flow... there is no source, there is no error handling option"* — a subflow has neither an inbound source component nor its own error-handling block, unlike a main flow.
- **Automatic dependency changes on import, noted directly**: importing the published API automatically adds entries to the project's `pom.xml` (the fragment dependency) and adds the **API Kit module** (e.g. version `1.5.11`) as a Mule plugin dependency — visible directly in the Maven configuration view, with the note that these versions can be manually bumped to newer releases if needed.

## Live Debug-Mode Test — Success and a Deliberate Error
- **Why Debug mode specifically, stated directly**: *"we need to know if the data is running properly, is it routing properly, who is doing it, what is it, we need to get a clear idea."* Two temporary loggers are added purely to visualize flow navigation during the walkthrough.
- **GET test, success path**: hitting `localhost:8081/employees/{id}` correctly routes through the listener → API Kit Router → the matching GET flow → returns the expected employee data as defined by the spec's example response. **A direct callback to an earlier-session bug**: hitting a *wrong* resource path (`employees1`, which doesn't exist in the spec) correctly produces an error — *"what happened to us earlier? We had to give a path in the listener, so the listener rejected it... that is the difference"* — contrasting listener-level rejection (wrong path entirely) with API-Kit-Router-level validation (right path, wrong data shape).
- **A practical Postman workflow tip, given directly**: rather than re-typing headers for every new request, **copy the full header block from a previously working request (Ctrl+A, Ctrl+C) and paste it into the new request's Headers tab using Bulk Edit (Ctrl+B)** — *"as a developer, you should know how to utilize the existing data... this is a smarter way."*
- **POST test, deliberately triggered error path**: a POST request is sent with a slightly malformed body. The API Kit Router correctly rejects it as a **400 Bad Request**, because — as reiterated directly — *"for the router, this particular API specification was used. The configuration was given by the API... the schema, data types, examples, everything was there properly. That's why I checked it and made this error."* This demonstrates the API Kit Router doing real, active schema enforcement, not just routing.
- **How the error response gets its shape**: the generated error-handling flow sets an `httpStatus` variable and a `payload` — *"by default... nothing will come [without this]... there is a variable and payload. Did we do all this or did we create it automatically? We created it automatically."* The variable/payload pairing corresponds to the **Error Responses Mapping** section of the HTTP Listener configuration, mapping specific error types to specific HTTP status codes and payload shapes — a design already covered in the prior error-handling sessions, now seen operating end-to-end on a real scaffolded project.

## Quick Recap
- **Publish to Exchange as standard practice** — required for Studio import and for API Manager policy application; not publishing is technically possible but not how real teams work.
- **Exchange organizes assets by type** (connectors, APIs, fragments, examples, policies, templates, etc.) across "All Assets," your org's own assets, "Shared with Me," and "My Applications" — with the type auto-detected when publishing from Design Center/Exchange itself, but manually specified when publishing a project from scratch.
- **Public Portal** shares a testable API with people entirely outside the organization, no login required — distinct from inviting named collaborators by email.
- **Import Published API (from Exchange) is the option genuinely used in real-time work**, over local-zip import (an SSL/connectivity fallback) or Design Center's direct connection.
- **Scaffolding generates a listener flow + API Kit Router + one flow per resource-method**, using an exact, auto-generated flow-naming pattern that the API Kit Router depends on — **never rename or reorder these specific generated flow names**, even though custom flows you build yourself can be named freely.
- **The API Kit Router performs real schema validation**, not just routing — demonstrated live via both a correct request (routed and processed normally) and a deliberately malformed one (correctly rejected as 400 Bad Request, using the same error-response variable/payload mechanism from earlier error-handling sessions).
