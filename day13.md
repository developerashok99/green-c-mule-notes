# Day 13 — HTTP Request Best Practices: Reconnection Strategy & Response Validator

## Session Agenda
- **Reconnection Strategy** — handling brief, intermittent network glitches automatically
- Applying Reconnection Strategy to a *source* connector (Salesforce), not just Request
- **Response Validator** (Success/Failure Status Code Validator) — customizing what counts as "success"

## Reconnection Strategy — the Motivating Problem, Explained With a Direct, Relatable Analogy

- **The core scenario, stated directly**: any HTTP Request call travels over a network — *"is there scope for this network to be vulnerable or not? ... no matter of milliseconds, if the network does not work, then your request will [fail]."*
- **The mobile-signal analogy, given directly, to distinguish a brief glitch from a real outage**: *"once we have a mobile phone, the signal will immediately go and auto-refresh in a matter of milliseconds... if the signal is lost and you check it again and refresh it, will it be convenient for you? Or [would you rather] restart the [phone] — which option will be good? Obviously, the first [auto-retry] option is better."* A **brief, intermittent** connectivity blip is fundamentally different from a genuine, sustained outage (*"if there's a half-hour [network] down, we can't do anything — even if we ping for half an hour, it will not come"*), and deserves a different handling strategy.
- **Without Reconnection Strategy, stated directly**: *"if I don't configure it, [an] HTTP connectivity error will come, and we will immediately send the error response as soon as the error comes"* — even if the *very next* attempt, a fraction of a second later, would have succeeded.
- **With Reconnection Strategy, stated directly and precisely, with a fully worked example**: *"if connectivity error happens, try 3 times, every 2000 milliseconds... first attempt: connectivity error. Try again after 2 seconds: connectivity error. Try again: connectivity error. Third attempt: connectivity [succeeds]. What happens now? There will be no error — the response will be sent."* Only if **every** retry attempt also fails does the connector finally give up and raise the real error.
- **The real cost of this, quantified directly, to be honest about the tradeoff**: *"if the response would normally come in 150 milliseconds... [but hits] 2 seconds plus 2 seconds [of retries]... that took 150 milliseconds, [but overall] 4 seconds [elapsed]"* — i.e., using this pattern does add real latency on the occasions where a retry is actually needed, which is a deliberate, accepted tradeoff for resilience against exactly the kind of brief glitches this feature targets.
- **Stated directly and emphatically as industry-standard practice**: *"this is compulsory, mandatory — as soon as you go [into a real job], this is one of the best practices... it can be for Salesforce connector, it can be for database connector, it can be for HTTP Request connector"* — a **universal, connector-agnostic concept**, not something specific to HTTP.

### The Three Configuration Options — Standard, None, Forever
| Option | Behavior |
|---|---|
| **None** | No reconnection at all — the original, no-retry behavior (default if unconfigured) |
| **Standard** | Retry a specific number of times, at a specific interval — **industry-common default cited directly: 2000 milliseconds, 3 attempts** (note: MuleSoft's own UI default shows "2 attempts," but this is *in addition to* the original attempt — *"a general attempt is going to happen plus 2 attempts without that"* — i.e., 3 total tries) |
| **Forever** | Keep retrying indefinitely, with no cap, until it eventually succeeds |

- **The exact, precise guidance on "Forever" — when it's wrong, and when it's actually fine**:
  - **Wrong for a request/response (synchronous) scenario**: *"if we are in the middle of the [request/response] process, we use Standard most of the time... [Forever means] until it is connected, [the caller/consumer] is waiting"* — a live consumer (e.g. a mobile app waiting on a response) cannot be kept waiting indefinitely; **Standard**, which eventually gives up and returns an error, is correct here.
  - **Genuinely fine for a *source*-side, event-driven connector**: fully worked example given directly, using **Salesforce's "On New Object" / "On Modified Object" trigger** (a **source** component, structurally locked to the Source section exactly like the HTTP Listener) — *"it will automatically trigger [when a new/changed record appears in Salesforce]... there is no such situation like sending a request and getting a response [synchronously] — it automatically connects to a system and gets the data from there... [so] I can use it forever [here]... nobody is getting impacted"* by the wait, since there's no live caller sitting on the other end expecting an immediate answer — it's just a background listener quietly waiting to notice new data whenever the network allows.
- **The general rule distilled directly**: *"where it will be — [for] connectors in the middle [of a request/response chain], we use Standard. For [source-level, event-driven] endpoints, we [may] use Forever"* — the deciding factor is whether a live, waiting consumer exists on the other end of the call.
- **Configuration location, same dual-level pattern as Response Timeout (Day 12)**: available at both the **Connector Configuration (Global Element)** level — applying to every operation sharing that config — and the **individual operation** level, for a specific override.

## A Direct, Extended Aside: How Real Production APIs Actually Handle Concurrent Load
Prompted by a student question about what happens when many requests hit an API "at once," the instructor gives a full, direct explanation, worth preserving:
- **An API has a processing capacity** (concrete example: *"500, 100, 50, 10..."* requests) — it creates instances to handle concurrent requests up to that capacity; requests beyond capacity get **rejected** with a bad/error response.
- **The reconnection strategy applies per-request, independently**: *"the connectivity error for any particular request will be [evaluated] for every instance"* — one request's retry sequence doesn't block or interfere with another's.
- **A real-world scaling example, given directly, using Swiggy (food delivery) as the illustration**: *"1 lakh people are ordering food from India... suppose there is a capacity of 5,000 per minute [per server] — what will they do? They will deploy it [across] 30-40 servers... [with] a load balancer"* routing each incoming request to whichever server currently has capacity. **The direct reasoning for *why* many servers instead of one big one is given too**: *"if I put it in one [single] API/server, and there is an issue in this server and it is down, then the whole application will be stopped"* — distributing across multiple servers is as much about **reliability** (no single point of failure) as it is about raw capacity.
- **A direct, honest correction of a natural beginner assumption**: *"in real time, it will not happen as we expected — when we test in Postman, [we assume] one request is processed, then the next... but [in production] it will not be like that"* — real traffic is highly concurrent, unlike the one-at-a-time mental model that naturally forms from solo Postman testing during development.

## Response Validator — Redefining What Counts As "Success"

- **The default behavior, stated directly and precisely**: *"if the status code is 200 [series] from there, it will treat it as success and send it to the next [step]. If it is not 200 series — 300, 400, 500, whatever the series — it will treat it as an error."* This is the built-in, unconfigured behavior of the HTTP Request connector.
- **The motivating exception, posed directly**: *"can I do it — [can I] treat a [non-200] error as [if it were] not an error?"* Yes — via the **Response Validator** section (under the Request operation's **Response** tab), with two configurable fields:
  - **Success Status Code Validator**: explicitly list which status codes (or ranges) should be treated as success, beyond the default 200 series.
  - **Failure Status Code Validator**: the inverse — explicitly list which codes should be treated as failure.
- **Range syntax demonstrated directly**: `400..499` — *"if you want to give [a] range, dot dot is in the middle — that means all the [values] in between."*
- **A fully worked, deliberately unusual example, demonstrated live to prove the mechanism genuinely works**: configuring the Success Status Code Validator as `200, 404` — then sending a request with a deliberately **wrong city name**, which normally returns a `404 Not Found` from the third-party weather API. **Confirmed directly, live**: with this configuration, the 404 is now treated as a **success**, and the flow proceeds past the HTTP Request step exactly as it would for a real 200 — *"we are asking 404 to also treat [as] success"* on purpose, and the debugger confirms this is exactly what happens.
- **Explicit, direct framing on how rarely this should actually be used**: *"it rarely comes, but in such situations, when it comes rarely, you should use this option"* — this is presented as a genuine escape hatch for unusual, specific business requirements (e.g. treating a "not found" as a valid, expected outcome for some particular workflow), not something to reach for casually.

## Closing Teaser: HTTPS, Tied Directly Back to API-Led Connectivity
- **A scenario posed directly, connecting back to Day 04's layered architecture**: *"this is our organization's network. This is an external endpoint... a request comes here [to the Experience API] — should this be HTTPS? ... From the Experience API to the Process API — which service should we use? HTTP. From Process to System? Same, HTTP."* **The precise, direct conclusion**: only the **outermost, internet-facing layer (Experience API)** genuinely needs HTTPS in a typical setup, since the layers *behind* it communicate purely within the organization's own private network — echoing (and reinforcing) the Day 03/Day 04 discussions on when HTTPS actually matters and how internal-vs-external exposure shapes real security decisions.
- **A quick, direct recap of *why* HTTPS matters, reusing the credit-card-number framing from Day 06**: *"we will send the credit card number... this is how the request is sent in HTTP — plain [text]. Now whoever is on the internet will sniff this... [but over HTTPS] since it can't decrypt it [without the key/algorithm], even if it sniffs this information, it won't extract it."* Full hands-on HTTPS configuration (trust store, key store, etc.) is explicitly flagged as a topic for a **separate, dedicated future session**, not covered here.

## Quick Recap
- **Reconnection Strategy** automatically retries a failed connector call a set number of times before genuinely giving up — protecting against brief, intermittent network glitches without adding real complexity to your own flow logic. **Standard** (a capped number of retries) is correct for synchronous request/response scenarios with a live, waiting caller; **Forever** is only appropriate for source-level, event-driven connectors (like a Salesforce "On New Object" trigger) where nothing is actively waiting on an immediate response.
- **This is a universal, connector-agnostic concept** — the exact same setting exists on Database, Salesforce, and HTTP Request connectors alike, configurable at either the shared Connector Configuration level or per individual operation.
- **Response Validator lets you redefine what counts as "success" beyond the default 200-series rule** — demonstrated live by deliberately treating a 404 as a success — a genuine but rarely-needed escape hatch for unusual business requirements.
- **HTTPS is typically only needed at the outermost, internet-facing layer** of an API-Led Connectivity architecture (the Experience API) — internal layer-to-layer traffic within your own enterprise network typically stays plain HTTP.
