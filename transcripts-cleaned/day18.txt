[Recap of deployment strategies] MuleSoft doesn't have its own data centres; it uses AWS and Azure. Even though AWS and Azure have data centres in India, MuleSoft hasn't prepared a CloudHub environment there. With no such data centres in India, the data would have to go to Singapore, London or US data centres — that's why some organisations didn't choose the CloudHub deployment strategy. Organisations without such restrictions and regulations go for the cloud deployment strategy. The cloud deployment strategy provided by MuleSoft is called CloudHub.

What will we do today? The definition of CloudHub, then horizontal scaling and vertical scaling, and then a demonstration.

[Agenda slide: CloudHub demonstration · Horizontal Scaling · Vertical Scaling · Q&A session.]

We need to know some CloudHub terms. First, what is CloudHub? CloudHub is an integration platform as a service (iPaaS). Say I need to deploy a MuleSoft application to a server. I'd have to set up the whole thing — Java, Maven, whatever is needed — configure and install all those services, and then it works; otherwise it won't. What does MuleSoft do? It takes the cloud environment and gets it ready for us — all the infrastructure — so we can deploy our application. CloudHub is such an environment.

Take an entire AWS server — since MuleSoft uses AWS a lot, they took the AWS cloud platform and installed everything properly — Java and whatever we need — ready to deploy MuleSoft applications. That's an integration platform as a service.

[slide — What is CloudHub? · CloudHub is an integration platform as a service (iPaaS) where you can deploy Mule applications in the cloud environment provided by MuleSoft · Worker is a dedicated Mule instance that runs your Mule application · vCore – worker sizes are measured in vCores (0.1 vCores – 500 MB, 0.2 vCores – 1 GB, 1 vCore – 1.5 GB).]

Could we take an AWS cloud and deploy a MuleSoft application to it directly? No — we'd have to prepare everything and set up the environment properly. Here they've done it all for us, and it's called CloudHub — an iPaaS platform provided by MuleSoft for cloud deployment.

When we deploy, where does it go? Into the CloudHub environment. How? Onto a worker. When I deploy the application, a worker is created in this environment, like a container, and our application is deployed in that worker. Compare with Anypoint Studio: where is our application deployed locally? In the Package Explorer, along with the dependencies, you'll find the server — Mule Server 4.4 (and 4.3). It's deployed inside that server, which has Java, Maven and everything ready. Same here: everything is ready, a worker is created, and our application is deployed in it.

A worker is a dedicated Mule instance that runs your Mule application. Think of it as a mini server — a dedicated, separate mini server capable of running that Mule application. Can you deploy multiple applications on a single worker? No. One worker runs one application; you cannot deploy a second application on it. That's why it's a dedicated Mule instance — a mini server that handles only one application.

As developers we have to decide on memory and workers — how much memory and CPU to give. In CloudHub that's called vCore: worker sizes are measured in vCores. Just as we measure distance in metres, kilometres and centimetres, they measure the size of workers in vCores.

How does MuleSoft licensing work? They charge based on how many vCores you've taken — one, two, three. Something like 25,000 dollars for one vCore, for maybe two or three years — I'm not sure exactly. There's a minimum number of vCores you have to take; in the beginning it comes to almost 70–80 lakhs, as far as I know, and it increases from there. So it's not that small organisations can't bear it, but it suits enterprise-level integrations — enterprise organisations.

When the application is deployed: 0.1 vCore, 0.2 vCore, 1 vCore and so on. 0.1 vCore means 500 MB of memory. Compare a phone with 2 GB of memory: with 10–15 apps it works normally without lag. With 25–30 apps, memory can't be assigned properly and the whole phone lags. In the same way, when we deploy an application to a worker, we have to give the right CPU and memory.

How do we know? We do performance testing in pre-prod — load testing. For this application we get 10,000 requests a day; how much per hour? We test a bit above that on one worker: can it handle it? Is the memory and CPU of one worker sufficient? We finalise it with the performance test. If it isn't done separately, the application just has to handle normal traffic, and since regular traffic isn't high, they aren't too concerned about load testing.

0.1 vCore is the minimum, with 500 MB, and it handles most applications. Very rarely we increase to 0.2 or 0.3. But there will be multiple workers everywhere, for high availability, as we discussed — if one worker crashes another is available, based on traffic. So: 0.1 vCore = 500 MB, 0.2 vCore = 1 GB, 1 vCore = 1.5 GB. The minimum is 0.1 vCore, by default — not less than that.

How many applications can be deployed with one vCore? If each is 0.1 — one-tenth — then 10 applications: 10 × 0.1 = 1. Can you hear everything? Yes. If I have 100 applications, I need vCores based on that. Enterprise architects check how many applications are coming and decide — there's a minimum of 2 or 3 vCores, how much extra, how much for production and non-production.

Horizontal scaling. Small example: the Flipkart application. The consumer sends requests to the load balancer. Our application is deployed on three workers — worker 1, 2, 3. Per day about 1 lakh requests come and these three handle them — a random example, not an exact calculation. The load balancer distributes requests from the front end.

Now they announce a festive-season sale and traffic becomes around 3 lakh a day. Say each worker can handle at most 40,000 requests a day [unclear: figures]. With three workers that's only 1,20,000. What happens with 3 lakh? It crashes. So we increase the number of workers. As we know the festival season is coming, we change the setting — the number of workers — in the configuration and deploy. The load balancer distributes even the heavy traffic.

[drawing: Flipkart sale — LB → workers; 1,00,000 → 3,40,000 requests.]

In real time the maximum number of workers is 8; we assign up to that per application, minimum 1. Needing more than 8 is very rare — I've never faced it.

The process of increasing the number of workers and deploying the application on multiple workers is horizontal scaling. When do we do it? When you want to process high-frequency, small-payload requests — the number of requests increases. It gives high availability, and the load is distributed uniformly. In interviews you may be asked when to go for horizontal scaling: whenever you need to process high frequency — a high number of requests — with the same payload size. In the festive example, did the payload size change? No — the same requests, just more of them. In such situations, horizontal scaling. Clear? Any questions?

[slide — Horizontal Scaling: The process of increasing number of workers and deploy application on multiple workers · If you want to process high frequency small payload requests, then go for HS · It provides high-availability.]

Next, vertical scaling: the process of increasing the vCore size of a worker. vCore size is basically memory. Say I gave 0.1 vCore and the memory isn't enough to handle the requests. Then we make it 0.2 — extra memory — and it can process. When does that happen? Say the payload is initially 200 KB, and we've been handling it fine. For some reason the payload size increases about 10 times. Can the same memory handle it? Only if there's capacity. If the requirement exceeds the capacity, it can't — the application crashes with out-of-memory issues. In such situations we go for vertical scaling. You should understand when to go for horizontal and when for vertical.

[slide — Vertical Scaling: The process of increasing the vCore size of a worker · If you want to process large payload requests with less frequency, then go for VS.]
[drawing: payload 200 KB → 2000 KB; 0.1 vCore → 0.2 vCore.]

What did I do? Every worker becomes 0.2 vCore. Then even at 2,000 KB it can handle requests with its memory. If I made only one worker 0.2 and kept the others at 0.1, what's the problem? With round robin, the first request is handled, the second goes out of memory, the third out of memory, the fourth fine, and so on. That's why the size must be increased for all workers, not just one. Clear?
