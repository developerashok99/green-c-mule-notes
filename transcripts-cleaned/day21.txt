[slide — What is RAML? RAML stands for RESTful API Modeling Language · RAML is a YAML-based modeling language to describe RESTful APIs and design API Specification · We define requests, responses, schemas, examples, resources, methods, security schemes in API Spec · Design Center of Anypoint Platform supports RAML and OAS (Swagger).]

RAML stands for RESTful API Modeling Language — a language that helps us design a REST API specification. A REST API specification is a document or file containing the request, the response, the security policies, what the error response looks like, schemas and examples — all packed together. It's a contract between consumer and service provider: send the request like this; the response comes like this; the error response like this. We discuss everything with the consumer and try to accommodate it.

RAML is YAML-based. We designed a YAML file [for properties] — it's that type, a bit enhanced. Simple English, easy to understand, not complicated.

What do we define in the specification? Requests, responses, schemas. What are schemas? The request will be in this structure, the response in this structure, the error in this structure — that's the schema. Values can differ, but the structure is always the same. Like a table: the table's columns are the schema and the values inside are the data. Four columns — the values in them differ, but the four columns, their names and details, never change. That's schema. I'll explain and show in detail. It's easy for those who've worked already, but for those new to the course, I'm explaining how the terms differ. Examples: how the request and response will look. Then the API is broken into resources; methods; security schemes. We define all of these in the API specification. That's why we prepare RAML, in Design Center in Anypoint Platform.

How many versions? RAML 1.0 and 0.8; Design Center supports both. [unclear: they aren't the latest / RAML 1.0 is the latest supported by Design Center.] Do we use 0.8? I've shown a very simple example. Remember API-led architecture? Will the consumer send the request directly to one API, or through multiple APIs? Multiple. In our enterprise network: consumer → Experience API → Process API → System API → database. The System API communicates with the database and receives the response; then back to the Process API, the Experience API and the consumer. Why "experience"? Because it's exposed to the consumer, with very little activity — business logic goes in the Process API. All are REST APIs, and the response comes back the same way.
