In this session we will talk about JMS. In regular integration projects the requirements are REST, SOAP, database, JMS, the Salesforce connector and AWS S3. JMS is one of the most important requirements, and that's why we will look at JMS integration.

First, JMS is a generic term. For easy understanding: databases are provided by multiple vendors — MySQL, Oracle, Microsoft. Different databases are available in the market, and we have used MySQL. In the same way, JMS is a generic concept, used for communication between different systems and applications. What is JMS? Java Messaging Service — that's the full form. From the name it's clear: we establish communication in a message format.

[drawing: JMS = Java Messaging Service; brokers — RabbitMQ, Apache ActiveMQ, Apache Kafka, IBM MQ; Anypoint MQ (licensed); benefits: decoupling, asynchronous]

Are there companies that provide these messaging services? Many: RabbitMQ, Apache ActiveMQ, Apache Kafka, IBM MQ and others. Apache ActiveMQ is open source, so we will use it for practice and the demo. The terminology is the same across them — queue, topic, publisher, subscriber, producer, consumer, message. There may be small changes, but if you know one JMS service well, it's easy to understand the others. Apache ActiveMQ is open-source software from the Apache Software Foundation; it is completely free, so we can download, install and use it. The rest are licence-based.

MuleSoft also provides Anypoint MQ, a messaging service from MuleSoft. Along with it there's the VM connector — you can use VM as queue-based too; I'll tell you what we use when. Anypoint MQ is licence-based: even with a MuleSoft licence, you pay separately for Anypoint MQ. That's why we can't practise Anypoint MQ in the free version, so we won't discuss it. In the industry ActiveMQ is used more than Anypoint MQ, but depending on the organization they may use RabbitMQ, IBM MQ or other messaging services. That's the high-level overview. If we understand these two things, we can easily understand others.

[drawing: sender → JMS server / broker (ActiveMQ) with a queue or topic → receiver (subscriber/consumer); further processing handled by the receiver]

This messaging service is used as a mediator between different applications — a JMS broker. What do we do with a database? Insert a record and you can retrieve it permanently, update it, modify it, delete it. If we need permanent storage, we use a database. Now there is a JMS broker; I send a message to it. What do we call the one who sent the message? The producer — the one who publishes it: producer or publisher. I'll discuss the terminology in detail in a few minutes. So I produce a message and send it to the broker — we publish or produce the message into a queue or topic. After that, someone has to take it and use it: the consumer. They consume the message from that queue or topic and process it for the further business process.

For example, on this side there's a front-end application. It made a message and published it to JMS. In the back end there are three systems — one, two, three — and each department has its own business process. They have to take the same message and process it. After I produce the message and publish it, there's no rule that it must be removed immediately; you can take it when you need it, or remove it immediately, based on the setting.

The point to observe: the consumers don't know who sent the message. Is there any connection between the producer and the consumers? No — first point. And when the producer sends the message, does it have to be removed immediately? No; it can be removed when it's acknowledged. Then why not use a database — permanent storage with every record? With a database you'd have to delete the records yourself; JMS systems do all this automatically. To send to multiple systems, we use a topic: we publish the message to the topic; three systems take it from the topic, and after they're done, it is deleted from there automatically. So it acts as a mediator, a broker, between multiple systems. Even though the producer and consumer have no connection, communication is established.

When to use it? A producer is a system or application; a consumer is a system or application. Whenever you want to establish communication with decoupling. What is decoupling? Say there are four applications or four business processes; if I want to decouple them and process them independently, I can go for JMS. That's the first point. The second point is asynchronous. In synchronous communication, the producer sends the message, it gets processed, the response comes back through JMS to the producer. Here, the producer sends the message — and whether it was processed or executed successfully has nothing to do with the producer; it's not worried about it; it forgets about the further process. If we need multiple systems, we prefer the topic. To put it simply: there will be a message; we can take it and process it, or publish it to a system and send it to someone else. That's the overall context. Any doubts?

There's no coupling here: between producer systems and consumer systems there is no connection. The producer sent it and the consumers took it; the consumers don't know about the producer, or about each other. That's how we decouple producers and consumers. Is everyone clear?
