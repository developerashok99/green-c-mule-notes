[slide: Agenda — What is MUnit? Components of an MUnit test, capabilities of MUnit]

Today's agenda is unit testing in MuleSoft, with a framework called MUnit, and how to implement MUnits practically. In that process: what is MUnit, what components are there in it, what are the capabilities of the MUnit framework, and how to implement MUnits practically in projects. We will discuss all of these.

[slide: What is MUnit? — a Mule application testing framework for automated tests of integrations and APIs; full suite of integration and unit test capabilities, integrated with Maven for CI/CD]

First of all, simply put, it is an application testing framework. Generally we have many different tools; this one is part of MuleSoft, and MuleSoft has provided it to us as a framework. What is a framework? Everything is ready for us, so it reduces our work. With it we create automated tests for our applications, integrations, APIs and so on. What is the advantage of creating tests? We can check whether things work properly — it is very, very helpful for us.

Next, it is fully integrated with Maven as well, the project build tool. If you work in Java, there are JUnits. Since Mule is a Java-based tool, it is related to that: they created a new framework called MUnit to create tests easily. Because it is compatible with Maven, it is easy for us to run it through the CI/CD pipeline.

You can create tests in two ways: one is manual and the other is the recording option. The recording option works for Mule 4.3 and above; the previous versions didn't have it. Most projects are on 4.3 or above, so most of the time we go for recording. Error scenarios we can definitely handle too — so we use a combination: both manual and recording. We are learning both.

Let's take a general example of unit testing to understand it. Say a car has to be manufactured. What do we do? We manufacture all the parts individually. To make a car we need a lot of parts — I have taken some important ones: steering, gearbox, engine, seats, body, brakes, tyres and so on. We test each part individually to see whether it works, before assembling the car. Some parts may even be outsourced. Each works fine individually, but we also need to check that everything works together with proper coordination. After assembling, testing is done; once it passes, we send it to the sales office. If, when we assemble and test, the tyres are not working properly, what do we do? We replace the tyres. The test fails, we replace the parts, test again, and then send it to the sales office.

In the same way, what does a developer do? We develop an application, an API. In this API there are many individual flows. We create tests according to the input and check whether they work correctly. The developer creates the test in MuleSoft — recording or manual, either is fine. After creating the test, we run it, and it checks whether things work properly.

What is the use of unit testing? We have tested it now, and it is good. Now in the future we make a small change. We can check whether that small change has any effect. So we run unit tests at every level. What do we do with the MUnit framework? Before deploying the application, MUnit is one step in the pipeline.

[slide: Components of an MUnit test — Execution (run the flow with the input event), Behaviour (define the test behaviour), Validation (validate the result)]

In a Mule flow we have source, process and error sections. In the same way, when we create a test there are three sections: Behaviour, Execution and Validation. You can observe them here. Let's understand which section is used for what.

In the execution section, we execute the flow with the required input event. The execution section triggers the test, runs it, and provides the necessary inputs.

Next is behaviour. When the test runs, it behaves according to what we define here. We define some components and activities here. When the test runs, the behaviour section is utilized.

Finally, we have to validate. What is an automated test? Manually, what does the testing team do during API testing? They trigger the input in Postman and verify the response manually. MUnit is an automated test that we create. We have already given the input and also the expected output. Where do we define the expected output? In the validation section. It checks whether the result came according to it; if so, the test passes. If it is not according to the expected result defined in the validation section, the test fails. Then we check why it failed and fix it until the test case succeeds.

So, three sections. Execution starts the test with the required inputs. In the behaviour section, any behaviours we mention are utilized while the test runs. After the test runs, the result comes; if it matches the result given in the validation section, the test succeeds, otherwise it fails. That is how MUnit works.

Now the capabilities. The first capability: creating automated tests manually or using the recording option. Next, I told you it is a testing framework — MUnit is a testing framework provided by MuleSoft for MuleSoft developers to create automated test cases. For this we need some components in the behaviour section and some in the validation section. When we create a flow, listeners, flow references, loggers, Transform Message, Set Variable, Set Payload — all these are called message processors or components. Similarly, MUnit has its own components.

One is the mock processor — we use it a lot; it is the one we use the most. Where and when we use it, we will discuss, but understand the idea first. What is a mock in general? What is the difference between an actual interview and a mock interview? In the preparation stage, a mock interview behaves like the actual interview. In the same way, say I have a database: a mock component will behave in the same way and give the same result, but it will not make the actual database call. We will see in detail why we do that — it is very useful.

Next is the spy processor. Spy means just spy: it stands aside and watches whether the process is happening correctly — whether the entire process is being handled properly. There are components for that as well. Then the verify processor, which we use in the validation section.

One more thing: say we have created ten MUnit tests and I want to ignore one or two of them. We can ignore those tests — that capability is there. Among the ten, I want to tag some as error scenarios and some as success scenarios — that capability is there too. And I told you about the percentage: whether MUnit coverage is 70%, 80%, 50% or 30%, you can check it visually. It provides a coverage report in front of your eyes, and we can check all of this in Studio. When we go to the practical, we will discuss how to generate the coverage report, how to enable and disable a test, what components we use, and so on.

So for the flows, APIs and applications we create, the MUnits use this testing framework to create test cases, and they are automated. As soon as we run them, they automatically provide the same input, process it, compare the result with the expected result, and pass or fail the test. Any questions so far?
