What did we see in the previous session? We completed Parallel For Each, and before that For Each — both scopes in detail. Now batch processing. For the same kind of activity — processing data — we have been given three different provisions: For Each, Parallel For Each and batch processing. As I discussed yesterday, when we want to handle large data sets we go for batch processing.

Large data set is fine, but what counts as large? A generic example: someone wants to buy a car. For a normal employee earning Rs. 50,000, even a 10 lakh car is a burden — they have to consider all their expenses, pay the EMI and plan everything; for them, a 2 lakh car fits. It depends on that person's range — it's a relative term. In the same way, in batch processing, "large data set" is relative: we should know what to compare it with. The main thing is our memory. When the memory is in a situation where it can't handle the data — data sets larger than our memory — that's when we go for batch processing.

For example, our application has memory — say 500 MB — and with this 500 MB we process the entire application. A regular application with Parallel For Each: a listener, a process, a Parallel For Each. We process the data; memory is allocated to the application, and the internal variables and payloads are stored in memory. In situations where the memory cannot handle it — that's where batch processing comes in. Generally, when a data set grows to 20,000, 30,000 or 40,000, everyone automatically goes for batch processing. But from an interview point of view, the point to make is: whenever the data cannot be handled by memory — data sets larger than memory — that is one reason.

How many steps does a batch process take? First, multiple components are given to us for batch processing — in the Mule Palette in Anypoint Studio. How many phases does a batch process have? Three. First, Load and Dispatch; then Process Records; then the On Complete phase.

What happens in Load and Dispatch? This is the Batch Job scope. When we provide input to it, the first phase happens automatically in the background — we have no visibility of it anywhere. How does reliability come? Load into persistent queues: the data is split and saved into persistent queues.

[drawing: records loaded into a persistent queue; processing in memory vs persistent (disk)]

What are persistent queues? There are two types of queues — in-memory and persistent. We'll see queues in JMS. In-memory means: if the application restarts or crashes, the data in that queue is deleted. I publish a message to the queue; a consumer receives it and consumes it to process — I'll discuss this terminology with JMS. Say the message is here, stored in memory, and the application restarts: the memory is erased, and the data in the in-memory queue is deleted too. Persistent means: even if the application restarts or crashes, when we restart it, it continues from where it stopped. Since it already has the messages in the queue, it automatically takes them from the queue and processes them again. Where is it saved? On disk. That's why it's persistent: since it's saved on disk, it's available to us from wherever it crashed.

So in the first phase, when the batch job gets its input: load and dispatch — load into a persistent queue. That's the background step. The second phase is Process Records, which can have multiple steps — we do the entire processing there. Next is On Complete, the third phase. What is it? A summary of the total process: how many records were batched, how many processed successfully, how many failed — all presented as a summary.

In For Each, do we have to create a summary ourselves?
