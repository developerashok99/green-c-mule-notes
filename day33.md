## OAuth 2.0 — What It Actually Is
- **The full form, drawn out directly via a Q&A**: *"OAuth is a full form... Open Authorization... why am I talking about 2.0? Because there is also 1.0. Actually, 1.0... less secured and now it is not used in the industry [more used is] 2.0 more secured."* OAuth 1.0 is acknowledged as a real, earlier, less-secure predecessor — but the discussion focuses entirely on 2.0, since it's what's actually used in the industry today.
- **The precise, deliberately emphasized classification, stated directly and repeated for clarity**: *"it is an authorization framework. This is a framework... it is an authentication framework, not an authentication protocol. What is authentication?... just understand, OAuth stands for open authorization and the latest version is OAuth 2.0. OAuth is an Authorization Framework, not Authentication Protocol."* (The instructor's own phrasing briefly slips between "authentication framework" and "authorization framework" mid-explanation but immediately corrects and reiterates the intended precise point: OAuth is fundamentally about **authorization**, not authentication, even though the two get casually conflated in everyday usage.)

## Authentication vs. Authorization — The Hotel Analogy
- **The scenario, walked through step by step, directly**: a family books a hotel room online and arrives at the reception. *"What do they do after we entered the reception? They asked for details... booking ID... will they ask for address proof or ID proof? They will ask... all these are matching. What will they do then? They will give... access to a room in 100 rooms."*
- **Authentication, defined precisely from this scenario**: *"verifying the user's identity process is called authentication. That means whether the right user is coming or not."* — checking the booking ID and ID proof match is authentication.
- **Authorization, defined precisely, distinguished directly from authentication**: *"to that user, should we give access to the entire hotel or only to a particular room? Restricted access process is called authorization."* — being handed the key to room 405 specifically (not all 100 rooms) is authorization.
- **The strict ordering rule, stated directly and unambiguously**: *"will authentication happen after authorization or authorization after authentication? Authentication happens [first, then] authorization."* You must first verify *who* someone is before deciding *what* they're allowed to access.
- **The technical mapping onto API terminology, made directly and precisely**: *"in our API terminology, there are multiple resources in our API or there are multiple methods for one resource. I wanted to restrict the access exactly for a person... this is authorization coming into picture. And whether the request comes from the right user or client... for the API is authentication."* Concretely: verifying a client's identity (via client ID/secret, or credentials) is authentication; restricting that verified client to only certain resources/methods (e.g., access to Resource 1 but not Resource 2, 3, or 4) is authorization.
- **A related, precisely distinguished terminology point, given directly**: *"OpenID... this is authentication data. This is authorization data. But generally, we call it OAuth for everything."* — OAuth proper is authorization-focused; **OpenID (Connect)** is the related standard actually focused on authentication — but casual industry usage often blends the two under the single umbrella term "OAuth."

## Introducing the Authorization Code Grant Type — via Signing Up With a Third-Party Account
- **The everyday scenario used to motivate this, given directly**: creating a new account on a site like Zomato, Swiggy, or LinkedIn — with the direct observation that most such sites offer **two distinct paths**: entering your details directly, or **"Login with Google/Facebook/LinkedIn/GitHub."** **Why this second option is genuinely convenient, stated directly**: *"if you go to every app and remember the username and password, you will lose your head... the reason they have given that option is for convenience."*
- **A live demonstration on Geeks4Geeks's actual sign-up page**, walking through the real UI: direct email/password sign-up as one option, alongside Google/Facebook/LinkedIn/GitHub as alternative sign-up methods.

## Walking Through the Full Authorization Code Grant Flow
- **The scenario set up directly**: a user (Ramesh) wants to create a Zomato account using his existing Facebook account. Facebook's own APIs (profile details, friends list, photos, location tags) are described directly as living on Facebook's **resource server** — *"we call it resource server because it is deployed there."*
- **Step 1 — clicking "Login with Facebook" redirects to Facebook's own login page**, confirmed directly and precisely: *"did it go to Facebook or did it go to Jomato? It went to Facebook."*
- **Step 2 — the user enters Facebook credentials directly into Facebook's own page**, not Zomato's — an important security property implicitly reinforced throughout: *"you are giving username and password to your Facebook account... are you giving username and password to them [Zomato]? I am not giving username and password. If you give, it seems like compromise is over."*
- **Step 3 — the consent screen**, demonstrated live with a real Google sign-in consent prompt: *"by continuing, Google will share your name, email address, language preference and profile picture with Geek4Geeks."* **The scope of what's shared is explicitly limited and explicitly disclosed** — Zomato never sees the user's actual Facebook/Google password, only whatever specific fields the user consents to share.
- **Step 4 — after consent, the browser is redirected back to Zomato**, and the account is created using the shared details (name, email, profile photo where available) — demonstrated live via the actual Geeks4Geeks profile page populating from the Google account's shared fields.
- **Step 5 — what's actually happening "under the hood," walked through carefully with direct emphasis on things the user never sees**: the authorization server (Facebook/Google) generates a short-lived **authorization code** and needs to send it back to Zomato. **How it knows where to send it, explained via prior registration**: *"Jomato would have registered with them and created a process with them... they will be given an ID secret. It is called client ID secret or client secret. That means, Jometo has already registered this process with the Facebook authorization server."* Alongside this registration, a **redirect URI** was pre-configured — the exact endpoint Facebook/Google should send the generated code back to.
- **Step 6 — the authorization code arrives back at Zomato's server** (not directly usable yet) — Zomato then sends this code, together with its own registered **client ID and client secret**, to a **token endpoint** on the authorization server.
- **Step 7 — the authorization server validates all of this and issues an access token** back to Zomato.
- **Step 8 — Zomato uses the access token to call a scoped resource-server endpoint**, explicitly named directly as `get profiles` (deliberately **not** `edit profile`, `update profile`, or `delete profile`) — *"why? It only needs information... he is not in a hurry, right? What did he say when I gave the consent? It is already clear. She said she will give only a few details."* The resource server validates the token (communicating with the authorization server if needed) before returning the requested profile data.
- **A direct clarification on why the visible-in-browser authorization code is deliberately NOT used directly as the access token**: *"until this authorization code, everything happens in the front-end... this auth code will also be visible in the browser. Yes. If it is visible, anyone can use that token... that is why the auth code is taken and the token is generated by communicating with tomato and facebook in the backend."* The code-for-token exchange deliberately happens **server-to-server**, in the backend, specifically because anything visible in the browser is inherently interceptable.

## The Four OAuth Actors
- **Defined directly, mapped onto the worked Zomato/Facebook example**:
  - **Resource Owner** — *"is Ramesh the owner of the Facebook account or not?... he is called a resource owner."* The person whose data/resources are being accessed.
  - **Client** — Zomato itself: *"I am trying to utilize or on behalf of Ramesh, I am trying to get the details from Facebook. So I am called as client here."*
  - **Authorization Server** and **Resource Server** — both hosted by Facebook/Google in this example, precisely distinguished: the authorization server handles login/consent/token issuance; the resource server hosts the actual protected data/APIs (profile, friends list, etc.) that get accessed using the issued token. **Directly named real-world examples of authorization server products**: **Okta**, **Auth0**, or MuleSoft's own built-in capability via API Manager.
- **A direct mapping onto the MuleSoft ecosystem, worked through explicitly**: *"when we come to the MuleSoft ecosystem, what will be the resource server? Let's say it's a cloud hub... in our APIs, it's the workers, right?"* — the deployed API/worker plays the role of the resource server; an organization's chosen identity provider (API Manager's built-in mechanism, Okta, or Auth0) plays the role of the authorization server.

## Core OAuth Vocabulary, Defined Precisely
- **Grant Type**: *"the way you generate the... access token will be decided by this grantee [grant type]"* — different grant types represent different processes/flows for obtaining a token, suited to different scenarios. This session covers **Authorization Code Grant Type** in depth; **Client Credentials** and **Resource Owner Password Grant Type** are named and previewed for the next session.
- **Redirect URI**: *"this URI that the authorization server redirects the user after they have authorized the request. The redirect URI is specified by the client when it initiates the authorization"* — pre-registered by the client (Zomato) with the authorization server, so the server knows exactly where to send the generated code back to.
- **Authorization Code**: *"a temporary code that the client receives after the user authorizes the request"* — short-lived, visible in the browser/front-end, but never used directly as an access token.
- **Access Token**: *"a token that the client uses to make request to the resource server"* — with a stated typical lifetime given directly: *"1 hour, 2 hours, 24 hours, they basically keep it like this."*
- **Refresh Token**: *"a long-lived token that can be used to obtain a new access token when the current access token expires"* — explicitly noted as valid for a much longer period (example given: 10 days) than the access token itself, automating renewal so the client doesn't have to manually re-run the full authorization flow every time the access token expires. **A direct, honest usage note**: *"it is clear, but they use it less. Many people have no idea."*
- **Scope**: *"specific permissions that the client is requesting to access... the scope tells the level of access the client has"* — illustrated directly with a file-permissions analogy: one user granted only **read** access, another granted **read and write** but not **delete**, the resource owner retaining full read/write/delete access.
- **OAuth Actors**: *"the following agents, resource owner, resource server, client application, authorization server who are responsible for the entire OAuth process."*
- **OAuth Dance / OAuth Flow**: *"the series of steps involved in the entire OAuth process. The dance typically involves redirecting the user to the authorization server to grant permission, exchanging an authorization code for an access token, and utilizing the access token to access the protected resources."*

## Quick Recap
- **OAuth 2.0 is precisely an authorization framework, not an authentication protocol** — even though everyday usage often blends "OAuth" to cover both authentication and authorization loosely; **OpenID (Connect)** is the related standard focused specifically on authentication.
- **Authentication verifies *who* you are; authorization decides *what* you're allowed to access** — illustrated via a hotel check-in (ID verification = authentication; being given a key to one specific room, not the whole hotel = authorization) — authentication always happens first.
- **The Authorization Code Grant Type is used specifically for scenarios like "sign up/log in with Google/Facebook/LinkedIn"** — the client (e.g. Zomato) never sees the user's actual third-party password; it receives a short-lived authorization code (visible in the browser but not itself usable as a token) and exchanges it, server-to-server along with its own registered client ID/secret, for an access token.
- **The four OAuth actors**: **Resource Owner** (the end user), **Client** (the app requesting access on the user's behalf), **Authorization Server** (handles login/consent/token issuance — e.g. Okta, Auth0, or MuleSoft's built-in mechanism), and **Resource Server** (hosts the actual protected data/APIs — mapped to CloudHub workers in the MuleSoft ecosystem).
- **Core vocabulary**: grant type (decides *how* a token is obtained), redirect URI (pre-registered callback destination), authorization code (short-lived, exchanged server-to-server for a token), access token (short-lived, e.g. 1 hour, used to call protected resources), refresh token (long-lived, e.g. 10 days, automates renewing an expired access token), scope (the specific permissions granted, e.g. read-only vs. read-write).
- **The authorization code is deliberately never usable directly as an access token**, precisely because it's visible in the browser and therefore interceptable — the actual token exchange happens in a backend, server-to-server call.
- **Client Credentials Grant Type and Resource Owner Password Grant Type, plus JWT, are explicitly deferred** to the next session.
