## URI Parameters — Full, Precise Explanation

- **URI = Unique Resource Identifier.** **Also called "path parameter,"** with the exact reasoning given directly: *"because it is part of the resource path."*
- **Mechanics, shown directly**: `localhost:8081/employees/{employeeId}` — the actual value (e.g. `101`, `102`, `103`) is sent embedded directly **inside the URL path itself**, not appended after a `?`.
- **The precise reasoning for *when* to use a URI parameter, developed through a full worked example**:
  - APIs expose **resources** (e.g. an "employees" resource) that can be created/updated/deleted.
  - **The name-collision problem, stated directly, to motivate the *need* for uniqueness**: *"suppose I give 'Mahesh' [as a way to fetch an employee] — suppose there are 10 Mahesh in total — there will be scope for [confusion about] which one."* A name alone doesn't uniquely identify a specific resource instance.
  - **The fix**: use something that genuinely, uniquely identifies exactly one instance of that resource — **employee ID**, explicitly stated as *"specific and unique to each and every employee."* Other concrete real-world examples of this same principle given directly: a **bank account number**, or a **customer ID** — *"if there are 10 customers, the customer IDs and account IDs of those 10 members will be different and unique."*
  - **The precise rule, stated directly and memorably, using a "compulsory vs. optional" framing that recurs throughout this session**: *"if I am compulsorily identifying a parameter, and it is mandatory to send it compulsorily, then it will go to the URI parameter."* Concrete proof given directly: *"if I've set `localhost/employees` and have NOT sent the URI parameter — which employee should I fetch the details from? It is not possible, right?"* — i.e., without the identifying value, the request is fundamentally meaningless, which is the actual test for whether something belongs as a URI parameter.
- **Where a URI parameter is actually configured/declared, stated directly, with a real-world nuance**: *"where should it be assigned? It should be assigned in the Listener [path]. Actually, if we do not do anything in the Listener, where do we do it? We do it in the API specification, generally — you have to do it in either the Listener or the API specification when you define the resource. We do both in the same process [conceptually] — [but] most of the time, we do it in the API specification, [rather than purely] in real-time [ad-hoc Listener editing]."* I.e., while it's technically possible to just type the path pattern directly into a Listener's path field (as was informally done in earlier demo sessions), the **correct, real-world practice** is to define it formally as part of the RAML API specification during the Design phase.
- **Multiple URI parameters, shown directly with a worked example**: `.../departments/{departmentId}/employees/{employeeId}` — *"if I want, I will first pass the department ID to the employees... then I will send the employee ID related to that... even if there are multiple URI parameters, there will be scope [for that] — nothing to be worried [about]."*
- **Access syntax, demonstrated live via the Mule Debugger's "x+y" evaluator, exactly as established on Day 07**: `attributes.uriParams.employeeId` — with the same exact-casing discipline reiterated directly (*"U small and P caps"* in `uriParams`).
- **A precise, useful sub-point on inspecting *all* URI params at once**: evaluating just `attributes.uriParams` (with no specific key appended) returns **every** URI parameter present — *"if there are three [values], the key[s] will be printed... three values will be assigned to us"* — versus appending a specific key (e.g. `.employeeId`) to extract just that one value. The exact same dual-access pattern (whole-object vs. specific-key) is confirmed to work identically for `attributes.queryParams` as well.

## Query Parameters — Full, Precise Explanation, With Three Named Use Cases

- **Mechanics, restated and reinforced directly**: appended to the end of a URL, beginning with **`?`**, in **key=value** form, with multiple pairs joined by **`&`** — *"if there's multiple, it will be [joined like this]: key1=value1&key2=value2."*
- **The formal, three-part rule for when to use query parameters, stated directly**: *"query parameter is used to filter, sort, and paginate the collection of a result."*

### Use Case 1 — Filter, Fully Worked With Real Numbers
- **Scenario, with exact numbers given directly**: an organization has **50 total employees**; **45 are active**, and (as clarified through the discussion) **3 have gone "inactive"** (resigned) while **2 are "on leave"** (a distinct status from fully resigned) — the exact breakdown is refined live in conversation but the core mechanic is clear: different status values partition the 50 employees into distinct, filterable subsets.
- **The exact request→query mapping, given directly**: sending `?status=inactive` in the request maps directly to `SELECT * FROM employees WHERE status = 'inactive'` in the underlying database query — *"where does `status = inactive` come from? When I send a request from Postman, I send it through the query parameter... then, if I pass any [different] value — say `resigned` instead — [the underlying query condition changes to match] automatically."*
- **Access syntax, given directly**: `attributes.queryParams.status`, whose extracted value is then dropped directly into the dynamic query's WHERE clause — the exact same dynamic-binding pattern already established in Day 05's demo for `payload.employeeId`, just sourced from `attributes.queryParams` instead of `payload` this time.
- **A direct student question, precisely addressed — "isn't a URI parameter also a kind of filter?"** The instructor's precise distinction, given directly: *"if the status is inactive, it can be 10, 20, or 5 people — this is not unique, right? In such a situation, we go for [a query] parameter [instead of a URI parameter]."* The deciding factor remains **uniqueness**: URI parameters identify exactly *one* specific resource; query parameters narrow down a result set that can still legitimately contain **zero, one, or many** matching records.

### Use Case 1B — A Second Filter Example: Bank Statement Date Range
- **Scenario given directly**: a mobile banking app lets a user select a date range (example dates given directly: **November 10th to November 12th, 2024**) to generate a bank statement.
- **Mapped directly onto query parameters**: `fromDate=10-11-2024&toDate=12-11-2024`, sent alongside the account number (noted directly as sent in the **body**, distinct from the date-range values in the query parameters) — *"the database will take fromDate and toDate, collect [matching transactions], and send them in [the] return [response]."*
- **Explicit purpose of this second example, stated directly**: reinforcing that filtering via query parameters isn't limited to simple equality checks (like `status=inactive`) — range-based filtering (a date window) is an equally normal, common use of the same mechanism.

### Use Case 2 — Sort
- **Mechanics shown directly, with an exact example**: `?status=active&orderBySalary=asc` (or `desc` for descending) — combining a filter (`status=active`) with a sort instruction in the same request.
- **The exact worked outcome, described directly with named examples**: *"whole list of active employees is required... we have to sort those salaries — on what should we make ascending order? On the salary. For example, if we take these three: Ramesh [₹75,000] will come first, then Dinesh [₹1,50,000], then Mahesh [₹2,00,000]"* — i.e., the response's *record order* changes based purely on this one query parameter, with no change to *which* records are returned (that's still governed by the `status=active` filter).
- **The traffic-rule analogy, reused here specifically to justify *why* standards like this matter even though they're not strictly technically enforced**: *"if we don't have traffic rules, we can go anywhere — but if we have the same traffic rules, you will be safer... by following some rules and regulations, by following some standards, when we get into an API — oh, okay, this is passing to query parameters, this is passing in the body — the classification will be a little clearer. That is why we're trying to follow all these standards and practices."*

### Use Case 3 — Pagination, Fully Worked With Real Numbers (offset & limit)
- **The precise motivating problem, given directly, with real numbers**: *"a very big organization has 10,000 employees — out of these, 8,500 are actively working... if I load these 8,500 people at the same time to the front-end... is it easy to load 100 in the front-end? Yes. [Is it easy to load all 8,500 at once?] It would require a lot of memory and a lot of time to process."*
- **The fix — pagination**: *"instead of sending 8,500 in one case, we are sending 100, 100, 100, 100 [in successive chunks]."*
- **The exact mechanics of `offset` and `limit`, worked through with precise numbers, twice, for maximum clarity**:
  - **First worked example (limit=100)**: page 1 → `offset=0`, records 1-100. Page 2 → `offset=100`, records 101-200. Page 3 → `offset=200`, records 201-300. *"Every time I have to send 100, and from where I have to send — this offset will decide."* A 5th-page example is given directly too: *"what is the offset value for the 5th page? 401 to 500 — when I click on the 5th page, the offset is 400; then, automatically, from 401 to 500, they take all the values."*
  - **Second worked example (limit=15, a Flipkart-style product listing)**: page 1 → `offset=0`, `limit=15`, records 1-15. Page 2 → `offset=15`, records 16-30. Page 3 → `offset=30`, records 31-45. Page 4 → `offset=45`, records 46 onward. *"This decides from where to send it."*
- **Where offset/limit are actually sent, stated directly**: as **query parameters** — *"where do we send this offset and limit? We send it from the [query] parameters."*
- **How the specific chunk size (15? 100?) actually gets decided in practice — a genuinely useful, concrete answer, not a guess**: *"there will be a lot of discussion, a lot of testing, [around] page loading and speed[-up]. For example, if you send 25 [records], it takes 75ms; if you send 75 [records, maybe it takes longer, and] the customer will not pay attention [i.e., will lose patience]. There will be a lot of testing — [the exact number is] not random; testing is done [to determine it]."*
- **The critical business-context nuance, given directly with two contrasting concrete scenarios**:
  - **Customer-facing, revenue-sensitive (Flipkart phone search under ₹20,000)**: *"I have 10 seconds on my phone — I go to Amazon, or Chrome, or Google — there [are other options]. There is scope to [lose] business."* Slow pagination here has a real, measurable cost.
  - **Internal, back-office (HR requesting a list of all employees who resigned this month, via something like an Excel export)**: *"will they have any problem even if it takes 5 seconds? No. They can wait for 5 seconds. Do they have any customer experience or [risk of] business loss [here]? No."* The *same* underlying pagination mechanism is used, but the performance bar that actually matters is completely different depending on *who* is waiting and *what's at stake* if they wait longer.
- **A candid, direct personal disclosure on real-world frequency**: *"pagination is also a rare requirement — even I haven't worked [with it much] in real time"* — offered as an honest calibration of how often this specific technique (versus filter/sort, which come up more often) actually shows up in real project work.

## The Decision Rule, Stated as a Single, Clean Summary
> *"If it is mandatory or compulsory [to identify a specific resource], it is a URI parameter. If you have options [i.e., it's optional, used to filter/sort/paginate an otherwise-valid request], you [use] query parameters."*

- **Proof of "optional," demonstrated directly via a live before/after comparison**: sending the filter+sort example **without** the `orderBySalary` parameter still returns the full list of active employees — just in a **random, unsorted order** rather than an error. Similarly, omitting the `status` filter entirely still returns *all* employees (active and inactive together) rather than failing. **This is the actual, concrete test used, live, to determine "is this mandatory or optional?"** — not a guess, but demonstrated behavior.

## Strict Validation — the Misconception Explicitly Named and Corrected

### The Misconception, Stated Directly
*"A lot of people think that because I defined 5 [query parameters in my API specification], if I get more than 5, they will automatically [be rejected] — no, that's a wrong understanding."*

### Why This Genuinely Matters — the Security Angle, Explained With a Concrete Attack Scenario
- **The exact attack scenario given directly**: *"suppose I am a hacker, and I have 5 [legitimate] query parameters [my API expects] — instead, I will send 125 query parameters and send a huge amount of data... what will happen because of this? The application will crash."*
- **Where the actual fix lives**: after designing and importing the RAML into Studio, the generated **API Kit Router** configuration exposes a setting called **strict validation** — separately for **query parameters** and for **headers** (both named directly: *"query parameters strict validation... header strict validation"*).
- **What enabling it actually does, stated directly**: *"strictly what you have mentioned will be allowed in your API specification, and it will [reject anything else]... strictly what headers you have put, that will be [the only] valid [set], and it will say [so] clearly."* Without enabling this, MuleSoft will **accept** extra, undeclared query parameters/headers beyond what the RAML spec technically defines — the spec alone does *not* enforce a hard limit at runtime.
- **A second, deliberately concrete security example built out further, in the same discussion**: even with strict validation enabled to cap the *number* of parameters at exactly 5, each individual parameter's own **content** still needs its own restrictions — e.g. declaring a parameter as a `string` with `minLength`/`maxLength` bounds (concrete numbers given directly: **minimum 20, maximum 50 characters**). **The exact attack this specifically defends against, spelled out directly**: *"he sends 5 lakh characters to one of the query parameters. It will crash... it will come to our application beyond the security layer — our application will not manage, so it will crash. Validation is 20 characters, and this is more than 20 characters [so it gets correctly rejected instead]."*
- **Why URI parameters don't need this same strict-validation setting, explained directly**: *"URI params will already validate — it will not take anything extra, because it is part of your URL"* — since URI parameters are baked directly into the fixed URL path structure itself, there's no equivalent mechanism for "sending extra ones" the way there is with query parameters or headers appended freely to a request.

### `additionalProperties` — the Same Idea, Applied to the Request *Body*
- **Precise mechanism given directly**: within a RAML `type` definition describing an expected request body's schema, an **`additionalProperties`** flag controls whether fields **beyond** those explicitly declared in the schema are tolerated.
- **The default behavior, stated directly and precisely, correcting a second common misconception**: *"by default, it is true — if you don't mention it, you have to accept it by default [meaning, extra undeclared fields ARE accepted by default]... what will happen if you mention it [as false] here? It will not accept [extra fields]."*
- **A direct restatement of why this matters, tying it explicitly back to the same "myth" framing used for strict validation**: *"we have discussed all these in our interview questions — even in interviews, I will ask these questions. It is a myth kind of understanding — a false understanding [that RAML alone restricts things by default]."*

### An Honest, Direct Discussion of Real-World Adoption (Not Just Theory)
- **A student's direct, pointed question**: *"these are best practices, right? Why aren't we following them [in practice]?"*
- **The instructor's direct, candid answer, using the traffic-rule analogy once more, extended further**: *"human nature, that's it, exactly. If we have 100 rules, we follow 50 of them. That's why there should be more rules and punishment — if the architect is strict, automatically you have to follow; there is no other go."*
- **A genuinely honest, personal disclosure of real limits, given directly**: *"I know that there are no strict evaluations in the organizations I am currently working in. But still, if you look at it, you will agree [that they should be used]... it's better, if we're doing architecture on a project, to take care of some extra things and plan for it."* This is a real, specific example of the instructor modeling that **real practice often falls short of best practice**, and being transparent about that gap rather than pretending otherwise.
- **The specific, concrete factor that *does* correlate with organizations actually enabling strict validation, given directly with a full, real-world worked example**:
  - **Purely internal APIs**: lower real stakes, and — candidly — often left without strict validation in practice, even though it would still technically be good practice.
  - **APIs exposed to external third parties — the exact worked example given directly**: *"think of an ICICI bank — this bank is tied up with some NBFCs [Non-Banking Financial Companies] — for example, tied up with 10 NBFCs [named examples given directly: 'Aditya Birla,' 'Bajaj Finance'] — customers come to them, we have to approve the loans and disperse them. Now our API is being consumed by third parties AND by our own [organization]... if there are some differences between them [the different NBFC consumers], we have to change [things] every time — [so] it's better to put strict validations there."* The core reasoning given directly: *"there are multiple consumers in our API... in such situations, better is to put strict validations."*

## A Full, Worked Security Scenario Connecting Strict Validation Back to API-Led Connectivity (Day 04)
- **The scenario constructed directly, layer by layer**: an Experience API exposed to the internet, calling a Process API, which in turn calls **four separate System APIs** (one per backend system) — a mobile application is the consumer, reaching this whole chain over the internet.
- **The exact attack narrated directly, start to finish**: *"the employee who works here knows the username and password — he wants to crash our application. He has the username and password idea — he sends the [correct credentials], but sends 5 lakh characters to one of the query parameters."* Without a length restriction on that specific field, this oversized value passes the security/authentication layer successfully (since the *credentials* were valid) and then **crashes the application downstream**, precisely because *content*-level validation (string length limits) was missing even though *access*-level security (username/password) was properly in place.
- **The direct, concluding lesson**: *"it's very, very important to understand these things, and we have to decide how strong we are in terms of security... here, we have the highest security [need] — this API is exposed to the internet."* Security isn't a single yes/no gate (authentication) — it requires validation at **multiple layers**, including the specific content constraints on individual fields, especially once an API is genuinely internet-exposed.

## Quick Recap
- **URI parameter** = mandatory, uniquely identifies exactly *one* specific resource (an employee ID, an account number) — proven by the fact that omitting it makes the request meaningless. **Query parameter** = optional, refines an otherwise-already-valid request via **filter, sort, or paginate** — proven directly, live, by showing the request still succeeds (just with a different, unfiltered/unsorted result) when the parameter is omitted.
- **Pagination (`offset`/`limit`)** trades one large, slow response for many small, fast ones — the specific chunk size is an empirically-tested, performance-driven decision, and how much that performance actually matters is entirely dependent on *who* is waiting and *what's financially at stake* if they wait longer (a customer about to abandon a purchase vs. an HR employee who can easily tolerate a 5-second wait).
- **Declaring parameters/headers in a RAML spec does NOT, by itself, reject anything beyond what's declared** — that enforcement requires explicitly enabling the **API Kit Router's strict validation** settings (separately for query params and for headers), and, for the request body specifically, setting **`additionalProperties: false`.** Both defaults lean permissive, not restrictive, which is a genuinely common, real, and interview-relevant misconception to correct.
- **Real-world enforcement of these best practices is inconsistent** — the instructor is directly, personally honest that even their own current workplace doesn't strictly enforce all of this — but enforcement correlates strongly with how **externally exposed** a given API actually is, with regulated, multi-third-party scenarios (a bank's API consumed by several partner NBFCs) being the clearest, most concrete real case for taking it seriously.
- **Security is layered, not a single gate** — a full worked attack scenario shows that valid authentication credentials alone don't protect against a downstream crash caused by missing *field-level* validation (e.g. an unbounded string length) — both access-level and content-level validation matter together, especially for any API genuinely exposed to the internet.
