# Day 14 — Property Files: Externalizing Config Per Environment, Run Configurations, and Secure Properties

## Session Agenda
- **Why** hardcoded connection details break across environments, and what "externalizing properties" actually means
- The 4-step process for property files: create files → configure a Global Element → reference properties in components → supply the environment at deploy time
- `.yaml` vs. `.properties` syntax
- Deploying via **Run/Debug Configurations** (not just right-click → Run)
- **Encryption and Secure Properties** — protecting sensitive values like database passwords

## Why This Matters — Stated Directly, With Explicit Framing on Its Real-World Weight
*"We have fewer questions [about this] in interviews, but we are utilizing this compulsorily in real-time work. This concept is very important, because the work is done in real time."* This is a rare, explicit signal from the instructor that a topic matters *more* for actual job performance than for interview success — worth taking seriously precisely because it's not being oversold as an interview topic.

## The Core Problem, Explained With a Direct, Worked Scenario

- **The setup**: an application has been developed and tested against **Dev** environment details (a specific database host, a specific third-party API host). Now it needs to be deployed to **UAT**, and eventually **Production** — each of which has its own **different** actual hosts, ports, and credentials.
- **The exact question posed and answered directly**: *"if I take the same application and deploy it in production, will their production details go? ... It will not go, right?"* — if the Dev-environment values are **hardcoded** directly into the connector configuration, deploying that same package to UAT or Production doesn't magically pick up the correct values for that environment — it keeps trying to use the Dev values, which is simply **wrong** (*"it was wrong mapping, right?"*).
- **The fix, defined directly and precisely**: *"I will externalize these details and create a property file for each environment. I will fill up the details related to which environment and map them dynamically. That's what externalization of properties is."*
- **The realistic environment count for this specific example project, stated directly, with an honest acknowledgment of the "ideal" list from Day 03**: *"ideally, we should have [the] Dev, SIT, UAT, Pre-Prod, Prod, DR [environments] — but in this particular application, we have only three: Dev, UAT, Prod... we don't need [more] that much."* A student's question about alternate naming (Stage, LT for load-testing, Post-Prod) is directly, briefly addressed: *"different terminologies, but ideally it would be like this"* — reinforcing that exact environment names vary by organization even when the underlying concepts are the same.
- **A concrete two-connector worked example, with made-up but illustrative values given directly**:
  - **Weather API (third-party) host**: `dev.api.openweathermap.org` (Dev) → `uat.api.openweathermap.org` (UAT) → `api.openweathermap.org` (Prod) — plus a different secret/API key per environment.
  - **Database host**: `10.1.25.50:3306` (Dev) → `10.1.25.51` (UAT) → `10.1.25.52` (Prod).
- **A direct, honest caveat about real-world messiness, worth preserving**: *"even our UAT has to use their Dev [environment of the third party]... there are such situations too"* — sometimes a third-party provider doesn't actually offer separate Dev/UAT/Prod environments of their own, forcing your own UAT to point at *their* single available (e.g. Dev-tier) endpoint. **The correct process for handling this ambiguity, stated directly**: *"after confirming these things with them in the mail communication, then you have to configure [the] respective details"* — get it in writing/email from the third party rather than guessing.

## `.yaml` vs. `.properties` — Two Syntaxes, No Technical Difference
- **Directly stated**: *"there is no significance in [which you choose] — there is no place where [one gives] more performance... it depends on the architect. Each person decides in their own way. There is no technical performance-related issue."* Purely a **team/organizational convention**, not a technical decision.
- **YAML syntax, demonstrated directly, with the exact indentation logic explained**: a top-level key (e.g. `http:`) followed by an indented block (via **Tab**) containing nested keys (e.g. `listener:`), which is itself followed by a further-indented block containing the actual leaf values (`host`, `port`, `path`). *"This colon, this space, this tab space... HTTP — there is a listener inside, and these three details are inside the listener."* **`#` marks a comment line** — used directly to add organizing section headers (e.g. `# Listener Configuration`, `# Weather Request Configuration`) — explicitly framed as a **best practice**, especially once a real project has "10-15 configurations": *"if many people do it [without headings], they will make it worse — don't do it like that."*
- **`.properties` syntax, shown directly as the alternate style** — flatter, dot-separated keys (e.g. `http.listener.host=...`) rather than YAML's nested-indentation structure — functionally equivalent, just a different textual convention.

## The 4-Step Process, Given Directly as a Repeatable Checklist

### Step 1 — Prepare a property file for each environment
- **Rule stated directly, generalized**: *"if I have 6 environments, [I make] 6 [files]. If [I have] 2, [I make] 2."* — exactly one file per real environment your project actually deploys to.
- **Where they live, tied directly back to Day 08's project structure**: inside `src/main/resources` — *"isn't this project a necessary resource [to run]? ... that's why we keep it here."* **Best practice demonstrated directly**: create a dedicated subfolder (conventionally named **`config`**) to hold all the environment property files together, rather than scattering them loose in `resources`.
- **What actually gets externalized — everything connector-related, not just the database**: demonstrated directly for both the **Listener** (host, port, path) and the **weather Request connector** (host, port, path, API key) — with a direct note on a real nuance: *"generally, you cannot hard-code [the Listener's] host — [but] port is compulsory [to externalize], because [e.g.] when deployed in CloudHub, if HTTP is 8081 and HTTPS is 8082... it has to be [something like] 8091/8092"* under certain deployment configurations (a direct connection to the April-batch course's own VPC/port-8091 discussion, for anyone cross-referencing) — *"I will tell you when that situation comes"* is given as an explicit forward-reference rather than full explanation at this point.

### Step 2 — Configure a "Configuration Properties" Global Element
- **Found directly via**: Global Elements → Create → **Global Configuration → Configuration Properties** (or simply searching "configuration property" in the creation dialog).
- **What it needs**: a reference to **which property file to load** — demonstrated first as a **hardcoded** file path (e.g. directly pointing at `dev.yaml`), then immediately corrected to be **dynamic** instead (see Step 4) — a deliberately hardcoded first pass, shown live, specifically to make clear *why* dynamic resolution is the actually-correct approach.
- **A small, practical path-resolution detail confirmed directly**: you only need to reference the file *relative to* `src/main/resources` (e.g. `config/dev.yaml`), not the full absolute project path — *"it will check the resources first."* Backslash vs. forward-slash in the path is noted as generally interchangeable, with forward-slash as the safe fallback if an issue ever comes up.

### Step 3 — Reference the property in each component's configuration
- **The exact syntax, given directly, in two distinct forms depending on context**:
  - **In a connector's plain configuration field** (e.g. the Listener's Host field): `${host}` — dollar sign, curly braces, the exact key name.
  - **Inside a DataWeave expression** (e.g. within Transform Message): a *different* syntax is required — `p('host')` — **directly and honestly flagged as an arbitrary-feeling rule, without a deeper justification offered**: *"I don't have any rule as to why we should do this — when you want to use the DataWeave expression [context], you [use] a small `p` and single quotes [with] the key name."* This is presented as something to simply memorize as a fact about DataWeave's own property-access function, not something with an intuitive deeper reason.
- **Confirmed directly, with a student's clarifying question answered precisely**: *"do we give the same host even in the test, [for example]? Why do we give the same host?"* — the **key name** (e.g. `host`) stays identical across every environment's property file; only the **value** assigned to that key differs per file (`dev.api.openweathermap.org` vs. `uat.api.openweathermap.org` vs. `api.openweathermap.org`) — the application code references the *key* the same way regardless of environment, and the correct *value* is resolved purely by which property file actually gets loaded at deploy time.

### Step 4 — Supply the actual environment name at deployment time (via Run/Debug Configuration)
- **The mechanism, explained directly**: the Configuration Properties Global Element's file-path field is made **dynamic**, referencing an environment-name variable (e.g. `${mule.env}`) *inside* the file path itself (e.g. resolving to `config/${mule.env}.yaml`) — so the *actual* file loaded depends entirely on whatever value is supplied for that one variable at deploy time.
- **The exact variable name is an organizational/architectural decision, not a MuleSoft rule, stated directly**: *"there will be a name, and it will be decided by the organization — for example, `mule.env`, or `env`... this is decided by the architect."*
- **Where you actually supply that value — this is the real payoff of the whole session, and where the "Run Configuration" (previewed on Day 09) finally gets its full, hands-on treatment**:
  1. **Run menu → Run Configurations** (or **Debug Configurations**) — rather than simply right-clicking the project and choosing plain Run.
  2. Create a **new configuration** (given a clear name, e.g. `prod-configuration`), select which specific **application/project** it applies to (useful once multiple projects are open in Studio simultaneously).
  3. Under the configuration's **Environment/Arguments** section, supply the actual variable and value — e.g. `mule.env = prod`.
  4. Running (or debugging) **using this specific configuration** — rather than a plain default Run — causes the Configuration Properties element to resolve `${mule.env}` to `prod`, load `config/prod.yaml`, and deploy with **Production's** actual values.
- **A deliberately-created, live-debugged mismatch, shown directly, to prove the mechanism (and reinforce prior lessons)**: after switching to the `prod` configuration, a request initially fails — traced, using the **Mule Debugger**, to (1) a leftover incorrect resource path (`/weather` vs. the actual configured `/weather/{city}`-style path) and, once fixed, (2) a **`404 City Not Found`** response from the real weather API for a deliberately-wrong test city — both genuine, realistic debugging steps, not scripted failures, directly reinforcing the debugging discipline modeled since Day 05.
- **Confirmed directly that switching between `.yaml` and `.properties` config files mid-project is fully supported** — demonstrated live by adding a second, `.properties`-style config file (`config1`) alongside the original `.yaml` files, and simply re-pointing the Configuration Properties Global Element's file reference to load from the new file/format instead — proving the mechanism is genuinely format-agnostic.

## Encryption and Secure Properties — Protecting Sensitive Values

### The Motivating Problem, Restated Directly
*"We gave the username, host, port, and password to the database [in the plain property file] — is it correct to put the password here? Actually, it is not correct. We should not put it here. Instead, we should encrypt it."* A plain-text property file checked into a code repository (or simply readable by anyone with file access) is a real security exposure for genuinely sensitive values — most notably passwords and API secrets.

### Encryption/Decryption, Explained With the WhatsApp Analogy
- **The core concept, given directly**: *"conversion of readable format to unreadable format is nothing but encryption."* **The WhatsApp end-to-end encryption analogy, given in full, directly**: *"Hi Ramesh, how are you?"* sent in plain text is trivially readable by an interceptor; converted to an encrypted, unreadable string before transmission, it's meaningless to anyone without the correct key/algorithm to decrypt it back — *"all this will happen automatically [in WhatsApp], but this is called encryption and decryption."*
- **Symmetric vs. asymmetric encryption, briefly distinguished directly, with an honest scope-limiting note**: *"symmetric [means] when you encrypt or decrypt [with] a key, it is [the same] key... asymmetric [uses] a different key [for] decrypting... asymmetric is more secure."* **Directly, explicitly deprioritized for depth**: *"we don't have to be experts on this"* — the practical, hands-on mechanism actually used (shown next) is what matters for this course, not deep cryptographic theory.

### The Practical Mechanism, Fully Demonstrated Step by Step
1. **Add the "Secure Properties" module** to the project. **A version-dependent nuance given directly, honestly**: *"in the latest version [7.17+], this will be directly in the [Mule] Palette"* via Add Modules; on the instructor's own older Studio version (**7.12.0**), it instead had to be **imported from Anypoint Exchange** first. **Proven live, directly, that this step genuinely matters**: removing the module and checking Global Elements confirms the Secure Properties configuration option **disappears** entirely — *"if we add it, [only then] it [will] come here."*
2. **Create a "Secure Properties Config" Global Element**, pointing at the specific property file containing the encrypted value(s), and specifying the **algorithm**, **key**, and **mode** used to encrypt them (matching exactly whatever was used to actually encrypt the value — decryption only works if these match precisely).
3. **Encrypt the sensitive value using MuleSoft's own online tool**, named and described directly: *"there is a website called Secure Properties [Tool]... provided by MuleSoft — you can encrypt and decrypt here."*
   - **Algorithm choice**: **AES** and **Blowfish** are the two commonly used options, named directly — *"we are not bothered about what the algorithm is about exactly"* (i.e., treated as a practical tool choice, not something requiring deep understanding).
   - **A real, live constraint discovered and corrected directly**: attempting a short custom key (e.g. `xyz1234`, 7 characters) with AES produces an error — *"AES key length is not sufficient... we need to use 16 bytes"* — the key is padded/extended (e.g. to `xyz12345678`-style, 16 characters) to satisfy this requirement. **A direct, useful contrast given**: Blowfish, by comparison, is more flexible on key length — *"however many letters you give, the key will be sufficient"* for Blowfish, unlike AES's strict 16-byte requirement.
   - **A direct, emphatic security reminder**: *"this key is very important — don't share it with anyone."*
4. **Mark the encrypted value in the property file using the required syntax**: `![...]` (an exclamation mark followed by square brackets wrapping the encrypted string) — *"this application will understand that this is an encrypted value... since this is encrypted, we are telling it to decrypt it."*
5. **Reference the secure value using the special `secure::` prefix syntax** (already introduced in the April-batch course's own notes, now shown here in the Green Cloud course's own hands-on context) — demonstrated directly in a connector config field as: `${secure::secretKey}`-style syntax, referencing the property key name.
6. **A real, live mistake made and corrected directly, worth preserving as an authentic debugging moment**: after setting everything up, a request still fails — traced back to a **forgotten `secure::` prefix** on one specific reference (a plain `${key}` was left in place where `${secure::key}` was actually needed) — *"we forgot this step... it will directly take the encrypted [garbled] value [instead of decrypting it first]."* Fixing the missing prefix resolves it — another genuine, unscripted debugging sequence.
- **A direct, practical scope note on how many secure values a real project typically needs**: *"mostly, there will be less [few] in [most] projects"* — commonly just 3-4 sensitive values needing this treatment, with a bulk/file-based approach for handling many at once explicitly mentioned as existing but **deliberately not covered** here, since it's rarely needed: *"that is not required at this point of time for you people."*

## A Small, Practical UI Clarification, Given Directly, Worth Noting
- **The Run/Debug toolbar buttons ("Play" and "Bug" icons) use whichever Run/Debug Configuration was *most recently* selected/used** — *"even if I click on it here, which configuration is in the first place, that configuration will be utilized."* If you've set up multiple named configurations (e.g. `dev-configuration`, `prod-configuration`), clicking the plain toolbar buttons re-runs whichever one was last active, rather than always defaulting to some fixed "first" one — worth being deliberate about which configuration is currently selected before using the quick toolbar shortcut, to avoid accidentally redeploying with the wrong environment's settings.

## Quick Recap
- **Hardcoding connector details (hosts, ports, credentials) breaks the moment you deploy the same application to a different environment** — the fix is externalizing every such value into a **property file per environment**, referenced dynamically rather than hardcoded.
- **The 4-step pattern**: (1) one property file per environment, organized in a `config` subfolder under `src/main/resources`; (2) a **Configuration Properties** Global Element pointing at the right file; (3) reference values in components via `${key}` (plain config fields) or `p('key')` (inside DataWeave); (4) make the file path itself dynamic (e.g. `${mule.env}`), and supply the actual environment name via **Run/Debug Configurations** at deploy time — not by hand-editing the file reference for every deployment.
- **`.yaml` and `.properties` are functionally identical choices** — purely a team/architect convention, with zero technical performance difference.
- **Sensitive values (passwords, API secrets) must never sit in plain text in a property file** — encrypt them via MuleSoft's Secure Properties Tool (AES needs exactly a 16-byte key; Blowfish is more flexible), mark them with `![...]` in the file, add the **Secure Properties module** and a matching **Secure Properties Config** Global Element, and reference them with the `secure::` prefix — a forgotten `secure::` prefix is a real, easy-to-make mistake that silently uses the raw encrypted garbage instead of the decrypted value.
