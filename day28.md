## Why Create Initial Variables At All
- The session opens by picking up exactly where the skeleton was left off: *"We have prepared everything like a skeleton in the previous session. What should we do now? We should improve it one by one."*
- **The core motivating problem, stated directly**: when an HTTP Request connector is used later in the flow, its response **overwrites the `attributes`** of the Mule event. *"When we see in the HTTP request, the attributes are overwritten."* If the original request's headers, URI params, query params, correlation ID, and transaction ID were only ever read from `attributes`, they become inaccessible the moment any outbound HTTP Request call happens.
- **The fix, given as standard practice across many companies**: as soon as the request lands, capture headers, correlation ID, transaction ID, URI params, and query params into **variables** — because *"variables cannot be overwritten... unless we overwrite it [deliberately]."* Variables persist through the rest of the flow regardless of what any connector does to `attributes`.
- **Where this capture happens**: via a **Transform Message** or **Set Variable** placed immediately after the flow starts (in the private/implementation flow, created via a flow reference from the public scaffolded flow) — this is exactly the "initial variables" step referenced throughout the rest of the session.

## Four Ways to Create the Same Initial Variables — Compared Live
- **Method 1 — multiple `Set Variable` components**: one `Set Variable` per value needed (headers, URI params, query params, correlation ID, transaction ID) — this means **5 separate Set Variable components** for 5 values, since *"if it is set variable, you can create only 1"* variable per component.
- **Method 2 — one `Transform Message` creating multiple independent variables**: *"Transform message is capable to create attributes, variables and payload. And if the variables are independent to each other, we can create more number of variables in transform message."* This is more compact — one component, five outputs — but only works because the five values have no dependency on each other.
- **Method 3 — a single variable holding a nested object**: instead of five separate variables, create **one** variable (e.g. `originalRequest`) whose value is an object with properties like `queryParams: attributes.queryParams`, `uriParams: ...`, `headers: ...` — *"in one variable, we are assigning multiple properties to each one of them."* A student directly suggests this alternative live, and the instructor confirms it as equally valid: *"what she suggested was also correct."*
- **Method 4 — payload also saved into a variable**, in addition to the other four, "to further utilize it" later in the flow.
- **The explicit conclusion — no single right answer**: *"there is no right or wrong method. You can follow anything."* — this is presented as something each organization decides for itself, and a developer should be comfortable reading and adapting to whichever pattern an existing project already uses (the instructor references cloning an existing API from Bitbucket specifically to observe "how the multiple set variables are used" in someone else's real project).

## The One Real Constraint: Independent vs. Dependent Variables
- A direct question is posed and answered as the one genuine technical constraint on the "create it however you like" freedom above: **"there is a dependency on URI parameters randomly. If I want to form values in query parameters, I need values from URI parameters. Will this work or not? It will not work."**
- **Why it fails**: within a single Transform Message (or in parallel Set Variables), values that depend on each other's *already-computed* result cannot be created together in one shot — *"there is a dependency... we have to create a set variable in the next variable... after the URL parameter is formed, we have a dependency on it, so we have to create a set variable in the next variable."*
- **The rule stated plainly**: *"we have to create independent variables one by one. Since there is no dependency between them, everything will be created at the same time."* Only mutually independent variables can be created together in a single Transform Message; a variable that depends on another variable's value must be created afterward, in a separate step.
- **Direct guidance from "the architect"**: *"the architect said that we should utilize only set variables"* in some organizational conventions — in that case, if 5 independent values are needed, the answer is simply **5 Set Variable components**, or — if only one Set Variable is preferred — collapsing them into the single-object-variable pattern (Method 3 above).

## Switching to JSON Logger — Custom Connectors as an Organizational Pattern
- **The naming convention question raised directly**: is a plain `Logger` component's naming (start logger / end logger) good enough, or does the industry do something else? **The direct answer**: *"we use JSON logger. Actually, there are some extra beneficial functionalities in it."* Some organizations even build and use their own fully custom loggers.
- **JSON Logger as a connector, not a built-in component**: just like the HTTP Request connector needed a **connector configuration**, JSON Logger requires one too — created once at the **global** level and then reused: *"this global connector configuration for Jason Logger is applicable to each and every logger in the total project."* This avoids re-entering transaction ID / correlation ID mapping details into every single logger individually.
- **The Java-jar analogy, given directly**: *"in Java, if we put it in Java, there will be jars, right? That's it. Even here, we import the logger and use it for our project."*
- **The reuse mechanism explicitly tied back to Exchange**: *"if we don't have JSON Loggers, it's difficult to build custom Loggers for this particular organization... you publish them in the exchange and import them from the exchange."* This directly echoes the Day 26 lesson about Exchange as the central mechanism for sharing reusable assets (connectors, in this case a purpose-built logger) across an organization.

## The `indent` Property — Readability vs. Transportation Trade-off
- **What indent/indentation means, defined directly**: *"How is the line to line gap? How is the alignment?"* — i.e. whether the JSON output is pretty-printed across multiple lines or compacted onto a single line.
- **Default behavior**: indentation is **on by default** (`indent` defaults to `true`) — the printed payload/log is neatly formatted, one field per line.
- **Setting `indent = false`, demonstrated live**: the exact same content prints **without line breaks, all on one line**. **The trade-off stated directly**: *"Visibility, readability. This readability will be good [with indent true]. This readability will not be there [with indent false]."* But — *"is this good for transportation... Lightweight"* — the non-indented, compact form is smaller and cheaper to transmit/store, even though it's harder for a human to read at a glance.

## Log Levels — Info vs. Debug vs. Error, Briefly Introduced
- A student question about whether the "info" level matters is answered directly but deliberately kept light for this session: *"Even though it is an info, it doesn't have anything to do with it... Here only the level of error is giving information. But here we are trying to print whatever the information is."*
- **The core distinguishing behavior called out**: if a logger is set to a level like debug rather than info, *"it will print only when there is an error"* rather than printing every single time — which matters directly for performance/space: *"if you occupy too much space, the logger will not print [everything]. It will print only when there is an error."*
- **Deliberately deferred for later**: *"I don't want to confuse you with the functionality... we will discuss it separately. Let's leave it for now."* — signaling this is only a preview, with fuller treatment planned for another day.

## `app.name` and `flow.name` — Dynamic Identity Instead of Hardcoding
- **The question posed directly**: shouldn't the flow's name be hardcoded into every log message? **The answer, demonstrated live**: no — use the dynamic tokens **`app.name`** and **`flow.name`** instead of typing the literal flow name into the logger's message field.
- **Why this works and matters**: *"since it is in our post resource flow, that particular flow name will be printed. Now I have kept this same logger next to another one. That particular flow name will automatically take it. When this travels, if it is in any flow, that flow name will be printed."* Because the same logger configuration/message template can be copy-pasted across many flows and each instance will automatically report **its own** containing flow's name — no manual editing required per flow, and no risk of a copy-pasted logger silently reporting the wrong (stale, hardcoded) flow name.
- **The direct payoff, stated as a question and answered**: *"will we get clarity on which flow it is in? When the request passes?"* — Yes, precisely because the name is derived dynamically rather than typed once and forgotten.

## Trace Points: Start Logger, End Logger, and Middle/"Flow" Loggers
- **Naming discipline for loggers placed at different points in a flow, given directly**: *"I have set the start logger as the start logger. If I set the end logger, the request processing of the end logger is done. If it is in the middle, if it is before request, it is before request, before DBA, before DBA."* A logger placed mid-flow (e.g. immediately before or after a database call) is named to reflect exactly where it sits — `before DB`, `after DB`, etc. — rather than reusing generic "start"/"end" labels everywhere.
- **This position label is itself referred to as the "trace point"**: a small, deliberately hardcoded field capturing *"whether this particular flow has started or it is here or it is a small general message."*
- **A recommended, more structured logger message shape, given as an improvement over a plain free-text message**: application name, flow name, **source**, **destination**, **transaction ID**, **member ID** (or employee ID, in this project, since there's no separate "member ID" concept) — *"Since this is a different application, the transactions happen in a different system, so here the member ID and the transaction ID mappings are different."* The instructor explicitly walks through building this structured message field-by-field for both the start logger and (by copy-paste-and-adapt) the end logger, swapping `start time` for `end time` and `start DB time` for `end DB time` as appropriate.

## Measuring Elapsed Time with `now()` and Variables
- **The `now()` function, introduced via a direct question**: *"What does the now function do? Now is the data wave function. It prints the date and time."* Demonstrated live in the DataWeave Playground.
- **A live gotcha about timezone**: the printed date/time initially shows what looks like the wrong hour (*"2 am is visible here"*) — resolved directly: *"UTC time zone... that means... now I am keeping this here. Which server will take this now? In general, where the application is deployed."* **The rule stated plainly**: if deployed locally, `now()` reflects the local machine's timezone; if deployed to CloudHub, it reflects **CloudHub's default timezone, which is UTC** — *"if we want, we have to change it"* if a different timezone is required.
- **The practical use case for capturing `now()` into a `startTime` variable**: *"a post request came. It captures the start time of the post request... How long will the processing take? Will it take milliseconds?"* By capturing a start time near the beginning of the flow and an end time near the end (or bracketing a specific external call like the database), the difference between the two reveals exactly how long that segment took: *"You can check how much time it took between these two."*
- **Explicitly framed as optional, situational tooling, not a blanket rule**: *"Will you put it on everyone? There is no need to put it. But at one time, a situation like this came. Where does it take time? Why does it take time?... If we know that this is there now, will it be useful?"* — the instructor is teaching a diagnostic pattern to reach for when a real performance question arises (e.g. *"this database component... this is the start time and this is the end time"*), not something to instrument on every single logger by default.
- **The DB-specific version of this pattern, built live**: a dedicated `startDbTime` variable set immediately before the database call and an `endDbTime` set immediately after it — subtracting the two (`now() - now()`) gives the actual database round-trip duration in isolation from the rest of the flow's processing time.

## Why Logs Get Removed in Production, and Why Logging Doesn't Slow Down Responses
- **A real-world scenario recounted directly**: *"How do I check the logs in a production? What will be the rent? A production happened to us recently. In that, all the logs were reverted and sold to us."* — i.e., an entire production incident's logs were stripped/removed before being handed over, prompting the direct question: *"Why would you have removed it?"* The stated reason given: retaining large volumes of logs isn't free — *"the lawyer's insurance"* (log retention/storage) has a cost, and if there's no ongoing need, organizations may not keep it around.
- **Logging is explicitly stated to be asynchronous, and this is why it doesn't meaningfully cost response time**: *"logging is asynchronous in nature... it took me 5 milliseconds to print the logger. It took me only 1 millisecond to get past the logger. Now, is it saving 4 milliseconds or not? Because it's asynchronous... I take random numbers. Print it and then go to the next one."*
- **The printer-queue analogy, given directly to make this concrete**: *"you have a PDF for 100 printouts and you print it to 100. Will it be printed at the same time or will it be printed one by one? It will be printed one by one. But did I give the information that I need to the printer? Yes, I did. Will it work if it is in the queue? Yes, it will work. Can I do my work now? Yes, okay."* The flow hands the log line off to be written and immediately continues processing — it does not block waiting for the actual write/print to complete. **The direct reassurance given**: *"I don't have an impact on business during response time, right?... Many people will have confusion in real time"* about this exact point, which is precisely why it's called out explicitly.

## Introducing Sensitive Information and Masking
- **The problem stated directly, using the request payload as the concrete example**: the flow's payload contains fields like transaction ID, host, and **employee ID** early on — but what happens when a payload contains genuinely sensitive fields, and someone naively logs the *entire* payload? *"Many people print payloads. Here, nothing, just, I'm going to print this whole thing... What is the payload here? The payload is the same as the original request."*
- **What counts as sensitive information, listed directly**: *"Aadhaar card numbers, PAN numbers, mobile numbers. Or else, here, employee salary will come."* A concrete mobile number example is used: *"8, 9, 8, 8, 7, 7, 6, 6, 5, 4... I should not do this mobile number here"* fully exposed in a log.
- **A vivid, personal example of the real-world stakes, given directly**: *"There are 100 API developers. I am not able to match the salary of 100 API developers. My teammate will get angry..."* and later, a more concrete version: a newly-hired colleague's exact salary being visible in a production log simply because the developer had legitimate access to check logs for an unrelated reason — *"I interviewed him. He is going to join the company... I immediately went to the production and checked the log. See if I know his salary here... Is that clarity clear?"*
- **The compliance/regulatory framing, given as the serious, non-optional reason this matters in real organizations** — a direct RBI (Reserve Bank of India) audit scenario: *"someone from banks like... Reserve Bank of India, will suddenly come for audit. They will show your logs in production... if you want them to show sensitive information in inputs, you have to show them. They are not governing. You can't deny them."* Regulated industries (banking explicitly named) classify PAN, Aadhaar, credit/debit card numbers, email, and phone numbers as compulsory sensitive information, and an audit finding unmasked sensitive data in logs draws formal warnings — with real reputational and business consequences: *"if some bad reputation comes up in our organization, our employees will misuse the information. Then there will be a problem with the public listed company."*
- **The forward pointer to the actual fix**: *"masking function in the data view... we will utilize that mask function... we will see it tomorrow"* — the mechanics of the DataWeave `mask` function itself are explicitly deferred to the next session (Day 29).

## Quick Recap
- **HTTP Request connectors overwrite `attributes`** — that's why headers, URI params, query params, correlation ID, and transaction ID must be captured into **variables** immediately after the request arrives, since variables (unlike attributes) are not silently overwritten.
- **There are (at least) four valid ways** to create these initial variables — multiple Set Variables, one Transform Message with several independent outputs, a single variable holding a nested object, or a hybrid — with **no single right answer**; the one hard constraint is that **dependent variables cannot be created together** and must be sequenced (independent variables, on the other hand, can all be created at once).
- **JSON Logger is a custom connector**, configured once **globally** and reused everywhere — mirroring how organizations build and publish their own reusable custom loggers to Exchange rather than reinventing logging per project.
- **`indent`** trades readability (indented, multi-line, default `true`) against transportation efficiency (compact, single-line, `false`).
- **`app.name`/`flow.name`** are dynamic tokens that make a copy-pasted logger automatically report its *own* containing flow's identity, rather than a stale hardcoded name.
- **Loggers should be placed and named by "trace point"** (start, end, before DB, after DB, etc.), ideally with a structured message shape (application, flow, source, destination, transaction ID, member/employee ID).
- **`now()` reflects the deployment server's timezone** (UTC by default on CloudHub) and, paired with start/end variables, is a situational diagnostic tool for measuring elapsed time (including isolating DB call duration specifically) — not something to instrument everywhere by default.
- **Logging is asynchronous** and does not add to response time — the flow hands off the log line and moves on immediately, the same way handing a print job to a printer queue doesn't make you wait for the physical printout.
- **Sensitive information (Aadhaar, PAN, mobile numbers, salary, etc.) must never be logged unmasked** — a real compliance/audit risk (illustrated with an RBI bank-audit scenario), with the actual masking mechanism (the DataWeave `mask` function) deferred to the next session.
