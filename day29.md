## The `mask` Function — Importing and Using It
- Building directly on yesterday's cliffhanger, the session opens with the actual masking mechanics. A field is deliberately added to the payload for demonstration — a mobile number (`1234567890`) and a member ID — and the goal is to mask them both in the logger output.
- **The key discovery, stated directly**: masking isn't a built-in function available everywhere — *"this mask function will be in the availability of the data [library]... we have to import the utility from the values library."* Just like connectors need to be added to a project via Add Modules, DataWeave itself has libraries that must be explicitly imported before their functions are usable.
- **The exact import syntax given**: `import * from dw::util::values` — *"if there are other functions in this, one of the functions is mask, actually."*
- **How the `mask` function is applied, worked through live**: `mask(payload, {fields: ["mobileNumber", "memberId"]})` — Input is the payload, and the fields to mask are specified as a list of key names matching the payload's actual field names. A live syntax stumble is worked through: an initial attempt without matching the field's exact key name doesn't mask correctly, and the fix is simply using the correct field name as it appears in the JSON.
- **A clarifying point on function chaining syntax**: *"expression will be the input for the next function. If you don't put brackets, you will get confused... we will utilize these regular curved braces."*

## Masking at the Connector-Configuration Level — One Setting, Applied Everywhere
- Rather than calling `mask()` manually inside every single logger's message expression, the more scalable pattern demonstrated is: the **JSON Logger's global connector configuration** has a dedicated **masking fields** setting — a comma-separated list (e.g. mobile number, member ID) applied automatically to *every* logger that uses that configuration.
- **The direct payoff, stated as a rhetorical comparison**: *"I am using masking around 50 times out of 100 logs. Is it better to do it 50 times or one time? One time."* Setting masking once at the global connector level, rather than repeating the `mask()` call in every individual logger's expression, is the recommended approach.
- **Tied back to the custom-connector theme from Day 28**: *"Jason Logger is a custom logger. In our organization, we have an enterprise integration team. They will bill [build] custom loggers and provide these facilities... what if they don't provide it? This is how it works"* (i.e., falling back to manually importing `dw::util::values` and calling `mask()` directly).

## A Direct, Honest Discussion on Reading MuleSoft Documentation

I don't even remember what to do with the values. But why did I take it? I remember what I was doing. I went there and saw it and I remembered it."*
- **A frank admission about the official documentation's difficulty, given directly**: *"if we read the mules of documentation in the beginning, it gives us a lot of confusion. So, it's always good to start [elsewhere]... If 100 people read it, 5% will agree [understand it easily]. But 95% of the people who have watched it will not understand."*
- **The recommended learning path, given as a concrete strategy**: start with **DZone** — *"there is D-zone. There are different articles. Some developers like us, architects, they write articles with their interest. What they do is, they make it a little easy [compared to the main documentation]."* — or YouTube (community or official MuleSoft channel) — and only later work up to the official documentation once the fundamentals are comfortable: *"you have to inculcate a habit in such a way that you have to understand the MuleSoft documentation within 3-4 months... our final goal is to understand this documentation and get ready for it."*
- **The practical day-to-day workflow stated directly**: *"for example, we need another function. We will search for it and check in the official documentation and if there are any examples, we will know which library to import from."*

## Setting Up the Real MySQL Database and Table
- **Context reset**: MySQL was installed in an earlier session but no database or table had been created yet — *"we have installed the database. We have not done anything to create tables."*
- **A direct, honest scoping statement about how much database knowledge is actually required as a MuleSoft developer**: *"most of the time, we don't need to have full knowledge about the database. Basic commands like creating a table... even if you ask me, I know a little basic. But there is a new requirement. What I will do is... go to Google and read and understand everything there and immediately fulfill that requirement... I may not be able to do this complex work, but I will be able to manage it to a medium level."*
- **What a database is, defined directly**: *"a place where you can store your data permanently... whenever we want to store data on a permanent basis, we use databases."* **RDBMS vs. NoSQL, distinguished directly**: relational databases (Oracle, MySQL, Microsoft SQL Server) store structured data; NoSQL databases (MongoDB, named directly) store unstructured/object data. **A direct analogy for why SQL dialects differ slightly between vendors**: *"Java and .NET are both programming languages. Ultimately the result is same, but the way you implement will be a little bit different... if you compare MySQL and Oracle's SQL, there will be a slight difference [90-95% the same]. But if you look at .NET and Java, there will be a lot of differences."*
- **Creating the database**: `CREATE DATABASE mule` (executed in MySQL Workbench) — response: **"1 row affected"**, confirmed with a green success symbol. Re-running the same command produces a red error: *"can't create database, already exists."* Commands like `CREATE` are noted as **not case-sensitive**, though the actual row/column *data* is case-sensitive.
- **Selecting the database to use it**: `USE mule` (or the relevant database name).
- **Creating the table**, with the exact structure worked through field by field:
  - `employees_info` as the table name.
  - **`EMP_ID`** — `INT`, **NOT NULL**, and the **primary key** — justified directly: *"if there is no employee or employee ID in the organization, there should be no employee or employee ID in the organization. Honestly speaking. That's why it should be compulsory and not be null."*
  - **Employee name** — text, nullable in this example only to illustrate the contrast (*"generally, the name will also be compulsory. But still, I just kept it to show the difference"*).
  - **Employee status** — plain text, **not null**.
  - **Employee salary** — `DOUBLE` — explicitly chosen to accept decimals: *"the salary is 20,000 or 20 paisa. For example. Even if it comes like that... there is only a number allowed in the house"* (i.e., no strings, but decimals are expected).
  - **Employee designation** — text, capped at **50 characters**, default null.
  - **Primary key = `EMP_ID`** — its two guarantees explained directly: *"if the employee ID is not given when you insert it, it will not get inserted... if you give the same employee ID again, then it will not be inserted. It should be unique."*
- **Testing the empty table**: `SELECT * FROM employees_info` initially returns nothing.
- **Inserting a row live**: `INSERT INTO employees_info VALUES (...)` — a live length-limit bug is triggered deliberately: a name value longer than the column's allowed maximum length (255 characters) throws a red error, directly illustrating why knowing the database team's exact column data types and length constraints matters even without direct database access: *"you don't have access to the database... their team is handling it. Then how do you know? You have to ask him the table name, what are the data types, what is the capacity to allow maximum length."* After correcting the value, the insert succeeds (**1 row affected**) and a subsequent `SELECT *` confirms the row: employee ID 120, "Ravi," active, 80000 salary, Software Engineer designation.

## Why a Local MuleSoft App Can't Reach the Database — and How Real Orgs Fix It
- A direct question is posed and answered plainly: can the MuleSoft application (running locally) connect to this MySQL database (also local, on the same machine, but conceptually representing a database team's separate server)? **Answer**: only because they happen to be on the same machine in this training demo. In a real scenario, *"this is in your local, so it is not yet shared. It is in local and there is no [network] connection between our system and your system."*
- **What happens once the MuleSoft app is deployed to CloudHub, asked and answered directly**: *"will it work with the database or not? It will work... How will it work if it is deployed in the cloud hub?... your database is still there... that's why obviously if we test it locally, it will be [connected]."* But a genuinely remote database (not on the same machine) requires actual network connectivity between CloudHub and wherever the database lives — solved in real organizations via **private network connections**: *"database servers are placed in a shared location. So, they give connectivity to the database location and to the cloud hub... by giving a connection through a private network."*

## Property Files for the Database — Environment Mismatches, Explained Directly
- **Why the database connection details must be externalized to property files, explained directly via a rhetorical question and answer**: *"is this insert common for all these requests, right?... you have to change it environment-wise. For example, you are deploying the application in Dev at first. You gave it to Dev, hardcoded it and deployed it. So you have to change it to SIT."*
- **A genuinely practical environment-count mismatch scenario, raised directly and resolved**: MuleSoft/the application side has **4 environments** (Dev, SIT, UAT, Prod), but the database team may only provide **3** (Dev, UAT, Prod — no separate SIT database). **The direct guidance given**: *"don't get confused if you face such situations... before we take a decision, just discuss with other team people as well and take a final decision"* — e.g. deciding together whether the app's SIT environment should point at the DB team's Dev or UAT instance. This is explicitly framed as a real, recurring situation to expect and plan for, not an edge case.
- **Where the configuration goes, confirmed directly**: the database connector configuration is created **globally** (not per-flow), with **host and port** in a regular property file and **username/password in Secure Properties**, matching the exact same pattern from the earlier property-files session.

## Reconnection Strategy — Standard vs. Forever, Revisited
- **When to use Standard vs. Forever, given directly and concretely**: *"it is better to set standard when the transaction is in the middle or when the request is lost... when do we set forever? When there is no dependency [on the outcome]. The connector is the source. Or else, we are doing something in the last, in the asynchronous."* **Standard** is the default choice for most request-response scenarios like this database insert.
- **The recommended retry cadence, given directly as an "architect said" standard**: *"the best suggestion is to do it three times every two seconds. This is the standard, actually. Otherwise, our architect said 2 or 5 times."*

## A Live Secure-Key Mismatch Bug
- A real, live-caught bug: the database password (encrypted via Secure Properties) fails to decrypt correctly — *"It's not working. Global property. We haven't configured it yet... it's a secure key, right? We don't know which key we used, right?"*
- **The fix, worked through live**: creating a fresh global property for the secure key (a "random dummy name" for demo purposes) and re-encrypting with that known key, rather than trying to guess or recover the original one — directly reinforcing the Day 27 warning that the AES key/mode must be tracked carefully and consistently, because losing track of it makes previously-encrypted values permanently unreadable.
- **A related aside on where the run configuration parameters actually live**: *"it will always be confusing for me... it is given in the run configuration, right?... but now, whether the application is run or not, if you give global properties here, it will pick up."* — Global properties are available regardless of whether the app was started via a specific run configuration, whereas run-configuration-only parameters are not.

## Root vs. Service Accounts — A Direct, Important Distinction
- **A direct question and answer about what credentials a database team actually hands over**: *"who will give all these? The whole database team will come. Will the username and password be given by the root username and root password? No."*
- **Why not root, explained directly**: *"there are many permissions for the root. What is the root? You can do almost everything like create, delete... they will create a user for us and give us the user details"* — scoped specifically to what the MuleSoft integration actually needs (e.g., insert/update/select, but likely **not** create-table permission unless specifically justified and requested).
- **The single most emphasized rule of this section, stated directly and unambiguously**: *"when we connect programmatically, when we communicate mission to mission, when we communicate application to application, you should never use human-related accounts. You should always use service-related users or service-related accounts."* **Why this matters concretely**: a personal/human account tied to an employee (e.g. "Mahesh") breaks if that person resigns — *"if I resign now, will that service account work or not? It will work."* A dedicated **service account**, non-human and organization-owned, keeps working regardless of staffing changes.

## Writing the Insert Query with Dynamic Input Parameters
- **The Insert query and its input parameters, built live**: rather than hardcoding values directly into the SQL text, **input parameters** are used, with the query text containing named placeholders and a separate **Input Parameters** mapping section supplying the actual values (e.g. `EMP_ID` mapped to `payload.employeeId`, employee name mapped to `payload.employeeName`, etc.).
- **A direct naming-discipline recommendation, given plainly**: *"it is always a good practice to maintain the same column names"* as the placeholder keys, specifically so that mapping many fields (the instructor notes this scales to "50 fields or 100 fields") stays unambiguous and easy to audit — *"if we refer to it... it will be neat without confusion."*
- **A live gotcha about expression mode**: attempting to reference `payload.something` directly in the Input Parameters field without marking it as an expression fails — *"should there be `fx` or not? There should be effects [fx]. Why? Because the mode is not working. Why effects? It is working only in expression mode. `Payload.` is not an expression"* by default in that field — the `fx` toggle must be explicitly enabled to treat the value as a DataWeave expression rather than a literal string.

## Live Testing: POST Success and Two Distinct Error Scenarios
- **Preparing the request in Postman**: headers and body assembled for a POST to `/employees`, with variables inspected during a Debug session to confirm headers and query params were captured correctly at the start of the flow, alongside the `startTime` variable.
- **Success path confirmed**: the API Kit Router validates and routes correctly to the POST resource flow; the info-level start logger prints "Post employees flow started" with the correct trace point and start time.
- **Error scenario 1 — a duplicate-key SQL error, triggered deliberately by re-sending the same employee ID**: the error surfaces as a real **DB Query Execution / SQL syntax** type error (specifically a duplicate-key constraint violation, since `EMP_ID` is the primary key) — *"duplicate 20,000 for key, employees information"* — correctly caught by the project's existing error handler (built and reused from Day 27), which sets the final response to **status code 400** with `error.description` as the message.
- **Error scenario 2 — DB connectivity failure, triggered by physically stopping the MySQL Windows service mid-test**: with a breakpoint set on the POST flow and the request resumed step-by-step, the request correctly matches the **DB connectivity** error type — *"could not obtain connection from data source."* **The Reconnection Strategy is then observed working live**: the MySQL service is restarted, the debugger is resumed, and the retry succeeds — the previously-failed insert now goes through cleanly (confirmed by there being no duplicate-key conflict, since the earlier failed attempt never actually wrote a row).
- **A direct clarification on the fallback path for unmatched errors, reiterated from Day 27's error-handler design**: *"if there is no error there, error type, then what will happen? Generic error. Any is there, right?... if these two types don't match, anything will come down here"* — i.e., any error type not explicitly handled falls through to the catch-all `ANY` handler at the end of the chain.
- **Session closes with a preview of what's next**: *"after that, we have to do HTTPS service, community service, and policy supply. We have to do all these one by one."*

## Quick Recap
- **The `mask` function lives in `dw::util::values`** and must be explicitly imported (`import * from dw::util::values`) before use — DataWeave, like the Studio module system, has libraries that aren't available by default.
- **Masking is best applied once, at the JSON Logger's global connector configuration** (a "masking fields" setting), rather than repeated inside every individual logger's message expression.
- **Reading MuleSoft documentation is hard even for experienced developers** — the recommended path is DZone/YouTube first, official documentation as a 3-4-month growth goal, and searching official docs specifically once a concrete new function/feature is needed.
- **The real Employees database and table were created**: `CREATE DATABASE`, `CREATE TABLE` with `EMP_ID INT NOT NULL PRIMARY KEY`, employee name/status/designation as text, salary as `DOUBLE`, followed by working `INSERT`/`SELECT` statements — including a live length-limit error caught and explained.
- **A local MuleSoft app can only reach a database it has actual network access to** — real organizations solve remote DB connectivity via **private network connections** between CloudHub and the database's location.
- **Database connection details go in property files**: host/port in regular properties, username/password in **Secure Properties** — with a realistic environment-count mismatch (4 app environments vs. 3 DB environments) requiring cross-team discussion to resolve, not silent assumption.
- **Reconnection Strategy**: **Standard** (a few retries, e.g. 3 times every 2 seconds) for normal request-response flows; **Forever** only when there's no dependency on the outcome (e.g. a pure source connector or fire-and-forget async work).
- **Never use human/personal accounts for machine-to-machine (application-to-application) communication** — always a dedicated, non-human **service account**, specifically because it doesn't break when an individual employee leaves.
- **Live-tested both success and two distinct error paths**: a duplicate-primary-key SQL error (caught by the existing error handler, 400 response) and a DB-connectivity failure triggered by stopping the MySQL service, with the Reconnection Strategy observed successfully retrying and recovering.
