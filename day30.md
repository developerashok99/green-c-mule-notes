## Remove Variable — Freeing Memory Deliberately
- **What it does and when to use it, stated directly**: *"we can remove one variable with the remove variable... if it is in the middle, somewhere close to the flows, if we feel that there is no need, if we feel that it is heavy there... we can use remove variable option."*
- **The mechanic**: give the name of the variable to remove; multiple variables can be removed with multiple Remove Variable components, one per variable.
- **The direct payoff, stated plainly**: *"we are deleting the variable. And if you delete the variable, the memory allocated for that variable will be saved, exactly. And it can be utilized by other resources of your application."* This is framed as a memory-hygiene practice worth applying to large/heavy variables that are no longer needed mid-flow — not something to reflexively apply to every small variable.

## Building PATCH: Update Query, Hardcoded vs. Mapped Values
- The PATCH implementation flow mirrors the POST flow's structure (before/after-DB loggers, same pattern), but swaps the Insert operation for **Update**.
- **A direct point about writing the query with or without input parameters**: it's entirely valid to embed values directly in the query text (hardcoded strings/numbers) rather than using input-parameter placeholders — *"without input parameters, don't you have to write this query directly?... you can put strings or number there and give it there. You can also write the values directly here."*
- **A concrete business-rule example worked through live**: employees are always created as **active** (no scope for inserting an inactive employee), but PATCH is where an employee's status can actually change from active to inactive. This status value could be hardcoded directly into the PATCH query (`employee_status = 'active'`) rather than mapped from the payload, depending on the actual business requirement.
- **Why input-parameter mapping (rather than embedding values inline) is preferred as a matter of code cleanliness, stated directly**: *"why am I writing it separately? For neat and clean code. If you see here, these are all column names, these are mapping for column names. If you change anything, it will be neat. Otherwise, if it is a big query, it will be clumsy... since it is SQL code, it needs to be neat and presentable."*
- **The single most emphasized discipline for query mapping, stated directly and revisited multiple times**: *"the left side should match with these [table columns]... indirectly these are table columns. Right side are the values we map... left side are the values we send to any system. We put the keys here. We map the values in our payload or in our variables."* Many developers get confused about which side is which — the instructor calls this out explicitly as a common point of confusion worth being deliberate about.
- **A discussion of scaling complexity for PATCH depending on real requirements**: rather than updating just salary/designation, a more complex PATCH might allow updating first name, last name, phone number, and more — handled either with one flexible query covering all possible fields, or with the update kept narrow and deliberately scoped (as done here, limited to designation and promotion/salary) — *"it is our wish to increase the complexity according to our requirement."*
- **A note on multi-statement SQL**, given as a forward pointer rather than something demonstrated: a single Database Update operation carries one query, but MuleSoft also provides an **Execute Script** operation for running multiple queries, or a **stored procedure** approach — *"I have never tried it, but if I want to execute multiple queries, we have an execute script here."*

## Keeping RAML and Implementation Responses Consistent — A Full Live Cycle
- **The motivating principle, stated directly**: *"in an organization, the APIs are permanent, but the resources... work permanently [i.e., change]. Today, an employee has left, another employee has come... RAML thinks the response structure is like this. But when it comes to implementation, if you check here, it is different. They will get confused again."* Any third-party consumer or teammate checking the RAML spec expects the implementation to match it exactly — a divergence between spec and reality is treated as a serious problem, not a minor inconsistency: *"it is always a good practice to implement in the RAML itself... if we change the response structure, we can directly use any field. We can do it, no problem. But, is this response matching or not? It is not matching. There are extra fields."*
- **The concrete extra fields being added to the actual success response**: `transactionId` and `employeeId`, alongside the existing `statusCode` and `message` — deemed useful information for the API consumer to have (*"which employee created it? For that, some transaction ID. Which employee ID? That employee ID. Would this information be good for the source who communicated the request for us?"*), but not yet reflected in the published RAML spec.
- **The correct workflow given directly for handling this discrepancy**: *"always do it in the design center, change it in API specification, publish it and update it to our studio. If you want to do it urgently, change it in the studio and update it in the design center."* A third option — importing the RAML API folder directly into `src/main/resources` in Studio — is explicitly called out as producing an **uneditable** copy, so it's not a real path for making spec changes.
- **The live Design Center walkthrough**: navigating to the API spec's examples/data-types sections for the POST response, adding `transactionId` and `employeeId` fields to both the **response example** and the **response data type** (both need updating, not just one) — a live JSON-syntax bug (a copy-pasted example missing/mismatched quote characters) throws a schema error, resolved by reformatting/fixing the quotes.
- **Publishing the updated spec bumps the version**: from `1.0.0` to **`1.0.1`**. **The direct clarification that Studio does NOT auto-update**: *"when I publish it, will my studio get updated or not? It will not get updated, we have to select it"* — via right-click → **Manage Modules** (or a shortcut), selecting the API spec dependency and choosing **Update Version**. A live hiccup where the "Apply and Close" dialog option doesn't appear is worked around by directly editing the version number in `pom.xml`.
- **A direct clarification on what re-scaffolding does and doesn't touch, given in response to a student's concern**: adding a new resource in RAML and re-scaffolding in Studio only generates an **empty private flow for the new resource** — existing resources' already-built private flows are left untouched: *"we won't overwrite all our changes? No, we won't... all the old resources already have private flows. We won't change them, they will remain the same."*

## A Live Bug: The Router Configuration Pointed at a Stale API Version
- After bumping the pom.xml dependency to `1.0.1` and testing the PATCH flow, the request fails with a **"RAML not found resource"** error — diagnosed live as a router-configuration mismatch, not a code bug: *"the issue came from the global, router configuration... you have checked in the router configuration, you have edited it... how is the API definition? ... this will search for 1.0.0.1. Is it here? We have already updated it with 1.0.1, right?"*
- **The root cause, precisely identified**: the API Kit Router's own configuration element (in the global config) has its **API Definition** field pointing to a specific, separately-tracked version string that does **not** automatically follow a pom.xml dependency bump — it must be manually updated to match, in addition to updating pom.xml. **A direct callback to the general lesson**: *"if we have changed something [in the API spec/version], we should [go check the router config too]... sometimes there will be an API name directly [in the config, no problem], but when it is mapped like this [to a version], there will be an issue"* if the version reference isn't kept current.
- **The fix**: correcting the router configuration's API Definition reference to point at `1.0.1`, saving, and rebuilding — after which the PATCH request succeeds against the actual database.

## Introducing the Validation Module
- The Validation module is introduced generically as a component for checking incoming data against expected shapes/values: *"this validation module is used to validate some details. For example, if you get an IP, check if it is a proper IP or not. Or if you get an URL, check if it is a string or not. Or if you get an email... empty array or empty string."*
- **`isNumber`, applied to a PATCH scenario checking `payload.affectedRows`**: rather than checking `> 0` or `!= 0`, the instructor demonstrates using **`isNumber` with a minimum value of 1 and maximum value of 1** — meaning exactly the value 1 is considered valid, anything else fails the check.
- **Custom error messages and mapping the failure to a specific error type, worked through live**: on validation failure, a message like *"no data updated for the employee passed in the request"* is set, and the error is deliberately mapped to a **custom error type** rather than the module's generic default (`VALIDATION:INVALID_NUMBER`).
- **Error Mapping, explained as a general mechanism available on (nearly) every component**: *"error mapping is for every component. For every component, there is error mapping for all the components that raise errors. It is not for Logger. It is for [e.g.] IsNumber... it is available for database connector, HTTP request connector, etc. It is very rarely used [elsewhere]. Error mapping is mostly available in [and used with] this validation module."* **How it works, given directly**: a component's default error type (left side) is remapped to a custom error type (right side) — *"as soon as this error comes, in this component, I am changing that error type."*
- **The exact namespace:identifier syntax required, given directly and precisely**: *"it is enough if the syntax is followed properly. If you observe the error type, it is similar to `HTTP:CONNECTIVITY` and `DB:CONNECTIVITY`. In the same way, it is enough if the structure is followed."* The custom error is defined as **`DB:NO_DATA_FOUND`** — *"colon, left side should have a value, right side should have a value... database is the namespace [and] identifier is `no_data_found`."* This directly echoes and reuses the same custom error type already present in the reused error handler from Day 27.
- **A live-caught bug demonstrating the consequence of skipping the mapping step**: deploying before the mapping is actually wired up causes the request to fail because the newly-defined error type "does not appear anywhere in the application" yet, so the error handler can't recognize it — directly reinforcing that defining a custom error type and actually mapping a component to raise it are two separate, both-necessary steps.
- **The completed flow**: a **Choice router** checks `payload.affectedRows == 0` — if true, a `raise error` with the custom `DB:NO_DATA_FOUND` type fires (caught by the reused error handler, setting `error.description` as the message and a chosen status code, demonstrated live as 400); if false, the flow proceeds to the success response as normal.
- **A brief exploration of other Validation module operations mentioned directly**: *"it can be null, it can be number, it can be string, empty string, blank string... this collection means array. Empty collection means if an empty array comes, then it is empty collection."*

## Building GET: Select, Java-Array Response Shape, and Mapping to JSON
- **Choosing between a URI-param variable and the raw attribute, discussed live**: the query's employee-ID input parameter can be sourced either from the earlier-created initial variable (`vars.uriParams.employeeId`) or directly from `attributes.uriParams.employeeId` — both work; the attribute is used directly here since it's already conveniently available.
- **How the Select operation's response is structured, explained directly and carefully**: *"which format will the response come from the database? Java format... it will come in array of objects."* **Why an array specifically**, explained via direct analogy to a JSON POST body containing multiple employees: *"is this an array? ... this is an object. Is this an array of objects? Yes. Each object is represented by one employee."* Even a Select query scoped to a single employee ID still returns a single-element array — *"even then, it will come the same. But, only one object will come."*
- **Mapping the array response, worked through live**: accessing the first (and here, only) element requires an array index — `payload[0].employeeName`, etc. **A direct clarification about the Java-to-JSON conversion boundary**: the Select response arrives in Java format (a "hash map," as described), and a Transform Message converts it into proper JSON for the final response — *"this is from Select. All of this is properly managed. Not our headache."* Employee status is checked directly (e.g., mapped from `EMP_status` in the raw DB row to a boolean-ish `active`/`inactive` concept in the response).

## The "Not Found" Choice: Still a Success Response, Not an Error
- **A direct, important design decision made explicit**: if the Select query returns no matching employee, the correct response is **not** an error — it's a **200 OK with a message like "employee details not found in the database"**: *"you should not send the error response. You should send the success response... employee details not found in the database and we will send it. Then it will come to 200 OK."*
- **Implementation**: a Choice router checks whether the returned payload is empty and branches accordingly — one branch sets the "not found" success message, the other proceeds with the normal employee-details response.
- **`isEmpty`/`!isEmpty` vs. `sizeOf(payload) == 0`, compared directly for performance**: *"what is the problem with the size of payload? The problem with the size of payload is that the payload is very large... it will load all the data, check the size and do it later... performance wise, which is better? [isEmpty] is better."* `isEmpty`/`isNotEmpty` short-circuits on whether *any* data exists without needing to fully load and count a potentially large array — a meaningful distinction called out explicitly for large datasets. The final condition used is **`!isEmpty(payload)`** (read as "is the payload NOT empty") to gate the success-with-data branch.

## Live Testing: PATCH and GET, Success and Failure
- **PATCH tested live**: an existing employee's salary and designation are updated (e.g., salary raised to 1 lakh, designation changed to "Senior Software Engineer"); the debugger confirms `affectedRows = 1` in the response payload.
- **GET tested live, success path**: hitting `/employees/{id}` for an existing employee returns the full mapped JSON detail — with a live debugging pass through the Java-format intermediate payload (`size: 1`, a hash-map-like structure) before the final Transform Message converts it to the expected JSON shape.
- **GET tested live, not-found path**: hitting a non-existent employee ID correctly returns `payload size: 0`, correctly triggers the Choice router's "not found" branch, and returns the friendly not-found message rather than an error — confirming the design decision above works as intended.
- **A live-caught final bug closing the session**: an "Error Handler does not provide name attribute on error" failure — diagnosed and fixed by copying the correctly-formed `name` attribute from another working error type in the reused error handler and matching it exactly on the newly added one.

## Quick Recap
- **Remove Variable** frees memory for variables no longer needed mid-flow — worth using for heavy variables, not mandatory for every small one.
- **PATCH's Update query follows the same left-side-is-table-columns, right-side-is-mapped-values discipline** as POST's Insert — a genuinely common point of confusion worth being deliberate about.
- **RAML and the actual implementation response must be kept in sync** — the correct workflow is Design Center first, publish, then update the version in Studio (`pom.xml` and/or Manage Modules); a stale reference in the **API Kit Router's own configuration** (its API Definition field) is a separate thing that must also be manually updated and is a realistic, easy-to-miss source of "resource not found" errors after a version bump.
- **The Validation module** (`isNumber`, min/max checks) combined with **Error Mapping** lets a component's generic error type be remapped to a custom, meaningful one (e.g. `DB:NO_DATA_FOUND`) — following the same `namespace:identifier` structure as built-in errors like `DB:CONNECTIVITY`.
- **A custom error type must both be defined AND actually mapped/raised somewhere** — defining it alone isn't enough; skipping the mapping step produces a live-caught deployment failure.
- **Select operations return an array of objects, even for a single row** — Java format initially, converted to JSON via Transform Message; accessing a single result still requires array indexing (`payload[0]`).
- **"No matching record found" is a success (200), not an error** — a direct, deliberate API design choice, implemented via a Choice router checking `!isEmpty(payload)`, which is also the more performant check compared to `sizeOf(payload) == 0` for potentially large datasets.
